# Web Scraper Service — API contract v1

Contract between the **scraper service** (this repository, Python + Crawlee)
and the **Flow Steward extension** `flowsteward.web-scraper` that calls it.
Source: the task document `docs/plans/web-scraper-extension-2026-11-12.md`,
revision 6 (sections 5–10), in the Flow Steward repository.

Normative files:

| File | Normative for |
|---|---|
| `openapi.yaml` | Routes, methods, parameters, status codes, which schema each body uses, the error codes each operation can return (`x-error-codes`), the outgoing webhook (`webhooks.scraper_event`) |
| `schemas/*.schema.json` | Every body shape and every enum (JSON Schema 2020-12). Each enum is defined once, as a named `$defs` entry, and referenced everywhere else |
| This README | Semantics: what the shapes mean, state machines, rules, defaults |
| `examples/` | Illustrations only (a small lamp shop `lumen-shop.example` with the templates `product` and `spare_part`); every example validates against its schema |

Where this README and a schema disagree, the schema wins for shape and this
README wins for behaviour; report the disagreement as a contract bug.
Changes made after the first publication are listed in `CHANGES.md` (all
additive within v1).

## 1. Conventions

**Authentication.** Every request, `GET /health` included, carries
`Authorization: Bearer <token>`, the service token of the `scraper_profile`
connection. A missing or wrong token is `401 unauthorized`. The service has
one token (set by its operator); there are no per-user tokens.

**Versioning.** Every API route is under `/v1`; only `/health` is
unversioned. Within v1 changes are additive only: new optional request
fields, new response fields, new error codes, new problem codes and new keys
of counter maps. Therefore:

- the service refuses unknown request fields (`422`, field code
  `unknown_field`), so a typo never passes silently;
- clients **ignore unknown response fields**, treat an unknown error code by
  its HTTP status, and treat an unknown `event_type` like `problem`
  (claim it, then complete it). `event.schema.json` lists the event types
  of this service version; a later v1 service that adds one adds it to the
  schema, so a client that validates bodies against an older copy must not
  reject an unknown `event_type` but route it like `problem`.

Everything else (renaming, removing, changing a meaning or a state machine)
needs `/v2`. `GET /health` lists the supported versions in
`service.api_versions`.

**Content types.** Requests with a body: `Content-Type: application/json`
(UTF-8), otherwise `415 unsupported_media_type`. Responses:
`application/json`, except `GET /v1/runs/{id}/result/download`
(`application/x-ndjson`) and `GET /v1/runs/{id}/unextracted` with
`Accept: application/x-ndjson`. Bodies above `limits.max_request_body_bytes`
are `413 request_too_large`. Every response carries `X-Request-Id`
(`req_…`), repeated as `error.request_id` in error bodies.

**Times.** RFC 3339, always UTC with `Z`, for example
`2026-11-12T09:14:03Z`; fractions of a second (up to 6 digits) are allowed.
Durations are integers with the unit in the field name (`_ms`, `_seconds`,
`_minutes`, `_days`, `_hours`).

**Identifiers.** Generated by the service as a prefix plus up to 64
alphanumerics (the service uses ULIDs): `run_`, `evt_`, `mrq_` (mapping
request), `clm_` (claim), `smp_` (sample), `req_` (request). Clients treat
them as opaque strings and never parse them.

**Site key.** Mappings belong to a *site*. The site key of a URL is its
host, IDNA-encoded to ASCII (punycode), lower-cased, a trailing dot removed,
**a leading `www.` removed**, and `:port` appended when the port is not the
scheme's default. `https://WWW.Lumen-Shop.example:443/x` → `lumen-shop.example`.
A job's `site` is the site key of `site_url`; in `url_list` mode every URL
has its own site and `sites[]` lists them (`site` is then the first one).

**Names.** One concept has one field name everywhere. A flat field that
refers to a field of a nested object elsewhere is prefixed with that object's
name (`claimant_job_id` = `claimant.job_id`, `platform_job_id` =
`platform.job_id`). Maps keyed by an enum (`passed_by_step`,
`pages_by_class`) are named `…_by_…`; a single value of the same enum is
`passed_at_step`.

**Field paths** in errors: dotted, array positions in brackets:
`max_pages`, `urls[3].url`, `profile.proxy_tiers[0].session_mode`.

**Pagination.** `GET /v1/runs`, `GET /v1/sites` and
`GET /v1/runs/{id}/unextracted` are cursor-paginated: query `limit`
(1–200, default 50) and `cursor`; the response is
`{"items": [...], "next_cursor": "..." | null}`. `next_cursor: null` means
the last page. Cursors are opaque and valid for 24 hours
(`400 invalid_cursor` afterwards); a `limit` outside 1–200 is
`422 validation_failed` with field `limit`. Order: runs newest first
(`created_at`, then `run_id`); sites by `site`; unextracted URLs by `url`.
`GET /v1/sites/{site}/mappings` is not paginated (`versions=all` returns the
whole history of the selected templates).

**Private addresses.** Every scrape target (`site_url`, `sitemap_url`,
`urls[]`, every discovered URL, every redirect hop, sample and analysis
URLs, robots.txt, every sitemap of a sitemap index, the proxy test's IP echo
URL) is resolved before it is fetched; a host is refused unless every
address it resolves to is globally routable — private, loopback,
link-local, unique-local, unspecified, shared (100.64.0.0/10), benchmark,
documentation, multicast, reserved and NAT64/6to4/Teredo addresses that
embed such an address are refused, and **a host that does not resolve is
refused too** (`private_address_refused` in validation; at run time the URL
is skipped and counted in `counters.urls_skipped.private_address`, or
listed as unextracted when it came from `urls` or a sitemap). The service's
own one-off fetches (analysis, samples, robots.txt, sitemaps without a
proxy) connect only to the address they checked; in the browser every
request of the page (JavaScript and meta redirects, frames, sub-resources)
is checked, and the final URL of a sample or analysis is checked again.
Inside a job the intermediate HTTP redirect hops of Crawlee's own client are
not seen; the final URL is checked (a decision of the service). The
**webhook URL and proxy endpoints are exempt**: the platform and the proxies
may sit on a private network or plain http (the normal self-hosted layout;
the service setting `WSS_WEBHOOK_ALLOW_PRIVATE`, default on, can forbid
private webhook URLs).

`POST /v1/analyze` and `POST /v1/samples` fetch like a job: HTTP through the profile's
first selected tier with the job `headers`; for a challenge (or a page that needs
JavaScript) **one browser session per request** that runs the job's protection route —
wait → click (only when the service allows it and the config's `challenge_click` asks for
it) → solver (likewise, `use_solver`) — within the config's caps (`max_clicks_per_job`,
`solver.max_solves_per_job`, counted per request). robots.txt and sitemaps answered with a
challenge over HTTP are read through that session after clearance. `passed_at_step` names
the route step that earned the clearance (`wait`, `click`, `solver`), or the browser when
the page passed by just being loaded in it; `null` when the challenge was not passed.

Both answers carry an optional `protection_trace` (added): one entry per URL of the request
that met a challenge — the proxy tier used (or `null`), the exit IP when already known
(usually `null`; no extra request is made for it), every route step tried or skipped in
order with its outcome (`wait` timed out after N s; `click`: frame found via `frames` /
`selector` / `none`, clicked at x,y, result after N s; `solver` skipped and why), the
names (never values) of the cookies set, and the final page title. No HTML. With
`debug: true` in the config the page after the last step is kept as a PNG (at most 4 MiB,
as long as samples) and `screenshot_id` names it: `GET /v1/screenshots/{id}`. A job's
`protection.traces` holds the same trace for its first 5 challenged pages. Every challenge
also gives one INFO log line with the same facts (no secrets, no proxy credentials).

Every browser context is given the place of its exit IP: timezone, locale (the country's
main official language, the same for every call — `de-DE` for a German exit; and with it
`Accept-Language`), geolocation and, in Camoufox, the WebRTC IP — resolved once per proxy
session through the service's IP echo (`WSS_IP_ECHO_URL`) and the bundled GeoIP database;
without a proxy, the host's public IP. The fingerprint preset is drawn so that its screen
holds the browser window. `protection_trace[].environment` records the values given
(`exit`) and the page's own view of them (`browser_view`).

**One identity per exit (added 2026-11-13).** A real visitor does not change GPU,
screen, platform or core count between two page loads from one IP. The service keeps
one browser identity — the fingerprint preset (UA/platform, screen, WebGL
vendor/renderer, `hardwareConcurrency`) and, in Camoufox, the font and voice set drawn
for it — per proxy account and tier and exit IP (while the exit IP is unknown: per
sticky proxy session; without a proxy: per host IP), and gives it to every context going
out through that exit: analysis, samples, job contexts and the protection report.
Identities persist on the data volume (`identities.json`), so they survive a restart.
`protection_trace[].environment.preset_id` (and the job's `protection.traces[]`) names
the identity; the same exit shows the same id. The exit's place (above) is applied on
top of it as before.

**Camoufox OS and canvas (added 2026-11-13).** Camoufox 0.5 covers the canvas
2D and WebGL readback with random data when the identity claims another OS or GPU than
the machine renders with (as `privacy.resistFingerprinting` does in Tor Browser; stock
Firefox does not) — so a Windows identity on the Linux image answers every canvas
readback with noise. Two job settings choose the launch, for analysis, samples, jobs and
the protection report alike: `browser_os` (`host` default = the machine's own OS, Linux
in the image; `windows`, `macos`, `linux`) and `canvas_noise` (`auto` default = Camoufox's rule above, `off` =
the page reads the host's real pixels whatever GPU the identity claims, `on` = always
random). Both are part of the identity key, so variants never share a fingerprint.
Chromium ignores them and claims the host OS too. On a test site (managed challenge) only the identities that claim the host's OS passed — with exact or noisy canvas
alike — so `host` is the default since 2026-11-13. `protection_trace[].environment` carries the effective
`browser_os`, `canvas_noise` and a self-check measured once per identity on a blank page
of that context before it navigates: `canvas_readback` / `webgl_readback` = `exact` (the
known fill came back), `noise` (anything else) or `unavailable`.

**Stop on the first failed challenge (added 2026-11-13).** Within one `POST /v1/analyze`
or `POST /v1/samples` call, once a URL of a host fails the protection route (a challenge
met and not passed after every allowed step), the route is not run again for that host
in that call:

- samples fetch nothing more of that host (no HTTP, no browser) and answer 200 at once
  with what they have, the optional `stopped` object (`reason: protection_not_passed`,
  `host`, the `url` that failed, `skipped_urls` = candidate pages of that host left
  unfetched) and a `protection_not_passed` warning;
- analysis reads robots.txt and sitemaps of that host over plain HTTP only; a challenged
  answer counts as the same failure (no second route); `warnings[]` carries
  `protection_not_passed`.

The warning's `message` names the host, the challenge kind, the steps tried and the
proxy tier in plain words, e.g. "www.example.com shows a Cloudflare interstitial
challenge that was not passed (waited 15 s, clicked the checkbox once, no solver
requested); proxy tier 1. No further pages of this host were fetched (9 pages skipped)."
`protection_trace` keeps one entry per challenged URL actually tried. Jobs keep their own
rules (tiers, block rule) and are not affected.

**What samples tried (added 2026-11-13).** Every `POST /v1/samples` answer
carries `explanation`: the discovery source and size (sitemap URLs, capped or not, the
start page's links), the counts (pages tried, loaded over HTTP / in the browser / reused,
samples, not target pages, challenged, failed, skipped), the URL-shape groups tried with the
product signals found on them, up to 60 pages with how each was loaded and what came of it,
the seconds spent, the next `hints` (product page selector, Only these URLs with a pattern
taken from a group with product signals, Discovery = crawl from a category start URL, the
click / Fetch mode for challenged pages) and a plain `summary`; the "found N of M target
pages" warning carries the summary too. The service logs one INFO line per analysis and per
samples call with the same counts. Candidates: the start page's same-site links are grouped
by URL shape (`/*-c<n>`, `/*-p<n>`, `/lt/*`: plain words kept, slugs and a category tree
collapsed into `*`, the last segment's id marker kept) and ONE link of each shape is tried
first — content groups before groups in header/nav/footer/menu containers, small groups
before large ones (12 products before a 1028-link menu) — a shape is dropped after 2 tried
pages without a sample and a shape that yields a sample is sampled on; pagination, sort,
filter and other query variants are never sampled. Sitemap URLs are probed the same way over
their shapes (largest first). With `discovery_mode` `auto` and a start URL below the site
root (a category), the start page's links come first and the sitemap after them. The start
page is read in the browser when the host needs it (a challenge), with Fetch mode `browser`,
or when its HTML is nearly empty (JavaScript), waiting up to 5 s for the network to settle.
`explanation.discovery.start_page` gives its `hrefs`, same-site links, other hosts, skipped
variants and the shapes with their sizes; every page tried lists its `status`,
`selector_found` and `links`.

**Variant sources on samples (added 2026-11-13).** Every sample
carries `variant_sources`: the variant sources found on that page, each a
ready-to-use `variant_source` with the variant `count`, `option_names`, a
normalised `example` and the source's `raw_keys` — in-page JSON (WooCommerce
variation form, a theme's product JSON block), JSON-LD/microdata `offers` lists
and `hasVariant`, and for Shopify and WooCommerce pages the shop's product
JSON (fetched once per sample through the call's session — for a host that
needed the browser, through the cleared browser context only — and kept with
the sample, so `POST /v1/mappings/test` applies a `shop_json` source without
fetching). `microdata` lists the page's schema.org microdata as JSON-LD-like
nodes. `explanation.variant_sources` sums them over the samples and the summary
names them ("variant sources: JSON in the page (form.variations_form
[data-product_variations]) on 3 of 4 samples (3 variants); …"). Repair samples of
a job (mapping requests) carry the in-page sources.

**The product first in `distilled_html`; `price_on_page` (added 2026-11-14).**
`distilled_html` gives the page's own content first, each part after a comment
`<!-- wss:section <name> at <path> -->`: `product-summary` (the product's summary
block — title, price, variant form: WooCommerce `.product .summary`/`.entry-summary`,
Magento `.product-info-main`, Shopify `.product__info`, `.product-summary`, a
schema.org `Product` microdata block), then `main-content` (`main`, `[role=main]`,
`#main`, `#content`, `#primary`, `.site-content`, `article`; the summary inside it
replaced by `<!-- wss: product summary, given above -->`), then `rest-of-page`
(header, menus, footer; the parts given above replaced by a comment). `<path>`
names where the part sits in the page (last six levels, e.g. `div#content.site-content >
div#product-6689.product > div.summary.entry-summary`): selectors are written
against the page, not against the sample's order. A page without such a block is
given in page order, as before. A `data-*` value longer than 400 characters keeps
its first 160 and ends `… [N characters cut]`, or `… [N characters cut; parsed in
variant_sources[i]]` when that attribute is a variant source of the sample (its
variants are in `variant_sources[i]`). `value` and `for` attributes are kept (a
variant `<select>`'s option slugs and its `<label for>`). Before this a heavy
header and mega menu could fill the 64 KB budget before the price block and the
variation form.
Every sample also has `price_on_page` (`shown`, `range`, `on_request`, `missing`):
what the page itself shows of its price (6.5).

**Jobs: crawl order and one context per session (changed 2026-11-13).** The links
of a crawled page are queued in this order: links that look like targets (`url_include`, an
active mapping's `url_patterns`, URL shapes of pages already found to be targets) at the
front of the queue, then content links one per URL shape first, then header/nav/footer/menu
links, then pagination/sort/filter variants — no longer the first 2000 hrefs in document
order. Each crawl session (sticky proxy session) keeps one browser context for all its pages
(cookies, storage, cache), instead of a fresh incognito context per page. A host that
answered plain HTTP with a challenge (or passed one in the browser) is loaded only in the
call's cleared browser tab from then on — no more HTTP probes of it.

**One load per URL, one tab, a visitor's pace (added 2026-11-13).** Within one analysis or
samples call every URL is loaded at most once over HTTP and at most once in the browser: a
page loaded (and cleared) for discovery — the start page — is the same page a sample takes.
The call's browser keeps one tab for all its pages: after a challenge passed, the cleared
tab goes on to the next page like a visitor, with a pause of `delay_min_seconds` ..
`delay_max_seconds` between navigations and the previous page of the same host as
`Referer`. A host that passed a challenge earlier in the call and is challenged again gets
the route once more (one more click, if allowed); its trace entry carries `passed_earlier`
(`url`, `step` of the earlier pass) and, when that second route fails too, the
`protection_not_passed` message says the host had passed earlier and was challenged again.

## 3. Configuration

### 3.1 Layers and merge

Three layers, highest priority first, each a `job_settings` object
(`job_config.schema.json#/$defs/job_settings`, every field optional):

1. `run_inputs` — the run form of `Scrape a site`;
2. `site_settings` — the `Site settings` step;
3. `profile.defaults` — the connection's defaults;
4. then the defaults of `job_config.schema.json`.

In a layer, a missing field, `null`, `""`, `[]` and `{}` all mean **not set**,
so an empty value in `Site settings` falls through to the connection default.
`false` and `0` are values. The extension converts form values before
calling: `urls` (array of strings) becomes `[{"url": ...}]`, and the rows of
`urls_file` (CSV with `url` and optional `key`, or one URL per line) are
appended after them as `{"url", "key"}`; the combined list is capped by
`limits.max_url_list_entries`. Entries are de-duplicated by
(canonical URL, key).

`POST /v1/config/validate` returns the merged `config`
(`job_config.schema.json`, every field present), `sources` (which layer
supplied each value), `errors` and `warnings`. When `errors` is non-empty,
`valid` is false and `config` is `null`; every problem is listed at once
(a value above a limit: `limit_exceeded` with `limit` and the field named),
so the workflow shows exactly what to change. Warnings change the merged
value and say so:

| Situation | Result |
|---|---|
| `challenge_click: true`, service does not allow the click | Warning `challenge_click_not_allowed`; merged value `false` |
| `use_solver: true`, service does not allow solvers | Warning `solver_not_allowed`; merged value `false` |
| `respect_robots: false`, override not allowed | Warning `robots_override_not_allowed`; merged value `true` |
| `urls` given outside `url_list` mode | Warning `invalid_value` on `urls`; ignored |
| `use_solver: true` (allowed) and no `profile.solver` | Error `solver_not_configured` |
| `challenge_click` or `use_solver` true (after the rules above) and a selected tier with `session_mode: rotating` | Error `rotating_proxy_with_challenge_handling` on that field |
| `browser` names a browser that `GET /health` reports `present: false` | Error `browser_not_available` (`auto` never fails) |
| `use_proxy_tiers` names a tier absent from `profile.proxy_tiers` | Error `proxy_tier_not_configured` |
| A target host resolves to a private address | Error `private_address_refused` |
| An entry of `required_fields` not in `fields` | Error `required_field_not_in_fields` |
| `delay_min_seconds` > `delay_max_seconds` | Error `delay_range_invalid` |
| A regex that does not compile | Error `pattern_invalid` |
| A forbidden header name | Error `header_not_allowed` |
| A secret a tier needs is absent (`user_password` without `password`) | Error `secret_missing` |

`POST /v1/runs` takes the merged `config` and validates it again with the
same rules; any error there is `422 validation_failed` and no job is
created. The warnings' corrections are already in the merged value, so a
config that `validate` accepted is accepted by `runs` unless the service's
limits changed in between.

### 3.2 Connection profile

`connection_profile.schema.json` is what the extension sends from the
connection with a request: `proxy_tiers` (0–3 entries, each `tier` 1–3 at
most once), `solver` (optional, version 1 challenge type `turnstile` only),
`defaults` (a `job_settings` layer; used only by `validate`) and `webhook`
(`url`, `signing_secret`; required for `POST /v1/runs`). The service URL and
token are not part of it.

Proxy tier rules: `custom_list` needs `proxy_urls` (credentials inside each
URL; `protocol`/`host`/`port`/`auth_mode` are then informational); every
other provider needs `protocol`, `host`, `port`; `auth_mode: user_password`
needs `username` and `password`; `session_mode: sticky` needs
`sticky_minutes`. A preset provider makes the service build the provider's
own username parameters for `country`, `city` and the sticky session;
`generic` uses plain `scheme://username:password@host:port` and ignores
geo fields. Lower tiers are tried first; the service escalates to the next
selected tier only on a block (never on an ordinary fetch error) and keeps
the escalation for that host for the rest of the job.

## 4. Jobs

### 4.1 States

`state` (`run_summary.schema.json#/$defs/run_state`):

| State | Meaning |
|---|---|
| `queued` | Accepted; waiting for a slot (`limits.max_concurrent_jobs`) |
| `running` | Discovering, fetching, extracting, waiting for mapping requests, re-extracting, writing the result |
| `waiting_for_credentials` | The job's proxy/solver secrets cannot be decrypted, or an upstream proxy explicitly refused authentication (HTTP/CONNECT 407 or a browser proxy-authentication error). Nothing further is fetched until Resume. Proxy IP allow-list refusal can enter this state without stored credentials |
| `stopping` | An operator stop was received; pages in progress are finished, then the result is written |
| `completed` | Final. The result file is written and `run_completed` was emitted |
| `failed` | Final. Unrecoverable error; no result; `run_failed` was emitted; `error` says why |

Allowed transitions (anything else never happens):

| From | To | When |
|---|---|---|
| — | `queued` | `POST /v1/runs` creates the job (201) |
| `queued` | `running` | A slot is free (FIFO by `created_at`) |
| `queued` | `completed` | `stop`: an empty result is written, `stop_reason: stopped` |
| `running` | `stopping` | `stop` |
| `running` | `waiting_for_credentials` | Secrets cannot be decrypted (`problem_code: waiting_for_credentials`), or the upstream proxy explicitly rejects authentication (`problem_code: proxy_auth_failed`) |
| `running` | `completed` | The completion condition (4.3) holds |
| `running` | `failed` | `crash_loop` (the service restarted 3 times within 10 minutes while the job was running), `storage_error`, `start_url_unreachable` (`site_url` failed every retry and no other discovery source exists), `robots_disallowed` (`site_url` disallowed and `respect_robots`), `internal_error` |
| `waiting_for_credentials` | `running` | `resume` with secrets that decrypt-and-cover the job, after credentials or the provider IP allow-list are approved |
| `waiting_for_credentials` | `stopping` | `stop` |
| `stopping` | `completed` | The completion condition holds (`stop_reason: stopped`) |
| `stopping` | `failed` | Unrecoverable error as above |

A job survives a service restart in `queued`, `running` and `stopping`
(continuing from its persisted queue and counters; finished pages are not
fetched again) and in `waiting_for_credentials`.

**Limits do not change the state.** When `max_records`, `max_pages`,
`max_duration_minutes`, `max_result_bytes` or the block rule is reached, the
job stays `running`: discovery is cut, nothing new is fetched, pages in
progress are finished, open mapping requests are still waited for (up to
their timeout) and stored pages are still re-extracted; then the job
completes normally with the matching `stop_reason`.

**Operator stop** (`stopping`) is harder: open mapping requests are
cancelled (`cancelled`), stored pages that wait for a repair are listed as
unextracted with reason `stopped`, pages in progress are finished.

`max_duration_minutes` counts time in `running` and `stopping` only.

### 4.2 `stop_reason` and `outcome`

`stop_reason` (`null` until final; `null` for `failed`):

| Value | Meaning |
|---|---|
| `finished` | Discovery ended by itself and every queued URL was processed |
| `max_records` | `records_extracted` reached `max_records` |
| `max_pages` | `pages_fetched` reached `max_pages` |
| `max_duration` | `max_duration_minutes` elapsed |
| `max_result_size` | The next record would have made the result exceed `limits.max_result_bytes`; that record is dropped and its page listed as unextracted (`stopped`) |
| `stopped` | Operator stop |
| `blocked` | **Added.** The site blocks almost every page and nothing allowed is left to try (4.6) |
| `site_unavailable` | **Added 2026-11-14.** A run of server errors, timeouts or network errors on a host, after growing pauses (4.9) |

`outcome` (`null` until `completed`; `null` for `failed`):

- `complete` if and only if **all** hold: `stop_reason` is `finished`,
  `max_records` or `max_pages`; no template has status `failed`; every entry
  of the unextracted list is outcome-neutral: reason `not_found`, or a URL
  **from a sitemap** refused with `robots_disallowed` or
  `private_address_refused` (the site's or the operator's decision, not a
  failure; the same reasons for a URL of an explicit `urls` list are not
  neutral). URLs never fetched because `max_records` or `max_pages` was
  reached are not listed at all (4.5).
- `partial` otherwise.

Per template (`templates[].status`): `ok` (worked throughout with the
version active at start), `repairing` (a mapping request is open; only
while running), `repaired` (at least one repair was activated during the
job), `failed` (given up: request failed or expired, or repair limits
spent). A final summary contains only `ok`, `repaired` and `failed`.

### 4.3 Completion condition

A `running` or `stopping` job becomes `completed` at the first moment all of
these hold (they are exactly the fields of `progress`):

1. `progress.discovery` is `finished` or `cut` (`cut` = a limit or a stop
   ended it);
2. `progress.queue_pending` = 0 and `progress.in_progress` = 0;
3. `progress.open_mapping_requests` = 0;
4. `progress.pending_reextraction` = 0 (no stored page waits for
   re-extraction under a newly activated version);
5. `progress.result_status` = `written`: the file is complete, flushed,
   its SHA-256 computed and the descriptor stored.

The result file is written only after 1–4 hold, and nothing is added to it
afterwards. Setting `state: completed`, `finished_at`, `outcome`,
`stop_reason` and creating the `run_completed` event happen in one
transaction; `GET /v1/runs/{id}/result` is available from that moment.

### 4.4 Discovery

| Mode | Behaviour |
|---|---|
| `sitemap` | Only sitemap URLs (`sitemap_url`, else robots.txt `Sitemap:` lines, else `/sitemap.xml`); index, text and gzip sitemaps; never follows links |
| `crawl` | Link crawl from `site_url` within the job's site key; never reads a sitemap |
| `sitemap_and_crawl` | Both, de-duplicated |
| `url_list` | Exactly `urls`; discovers nothing; `site_url` ignored; robots.txt still honoured per URL when `respect_robots` |
| `auto` | Decided at job start (`resolved.discovery_mode`, with `resolved.reasons`) by the rule below; `POST /v1/analyze` recommends by the same rule |

`auto` rule: no sitemap, or a sitemap with no URL left after
`url_include`/`url_exclude` → `crawl`; otherwise `sitemap` when
`target_share` ≥ 0.8 or unknown, else `sitemap_and_crawl`. `target_share` is
the share of target-looking links on the start page (links whose page is
expected to match a template or `target_page_selector`, judged by the URL
patterns of the site's active mappings and `url_include`) that the sitemap
contains. `single_page: true` skips discovery (`resolved.discovery_mode`
stays `null`).

`url_include` / `url_exclude` are Python `re` patterns searched in the
canonical URL; include first (when non-empty), then exclude.
`url_exclude` keeps a URL out of the queue in every mode. **`url_include`
says which pages are extracted, not which are followed:** a sitemap entry
(a page to scrape) is queued only when it matches; in `crawl` and
`sitemap_and_crawl` every in-site link that passes `url_exclude`,
robots.txt and the limits is followed, and a crawled page whose URL does not
match a non-empty `url_include` is `not_target` (its links are still
followed; nothing is stored, no record, it does not count towards
`max_records`). A crawled page that matches `url_include` and no template
counts as a target page (`no_template`). Samples and analysis prefer URLs
that match `url_include`.

**Crawl scope (added 2026-11-14).** Three separate controls: *what
to extract* — `url_include`; *where to walk* — `crawl_include` and the switch
`stay_in_section`; *never fetch* — `url_exclude`. With a scope set, a crawled
page's links are followed only when the page is the start page or matches the
scope (`crawl_include` patterns; `stay_in_section` adds the start URL and
everything below its path, its pagination included). From a walked page, a link
that leaves the scope is still queued when it looks like a target page
(`url_include`, an active mapping's `url_patterns`, URL shapes of pages already
found to be targets) — product URLs usually live outside the category path — or,
while no target can be told by URL yet, every link is queued (fetched, not
walked). A target page outside the scope is fetched and extracted, its links are
not followed. Links left out by the scope are counted in
`counters.urls_skipped.scope`. Samples respect the same scope when target pages
can be told by URL. Sitemap URLs are pages to extract and are not affected.

### 4.5 Page classes and the unextracted list

Every fetched page gets one `page_class`
(`run_summary.schema.json#/$defs/page_class`; counted in
`counters.pages_by_class`):

| Class | Meaning | Repair |
|---|---|---|
| `extracted` | A template matched and every required field is filled; a record was written | — |
| `not_target` | No template matched and the page does not look like a target page; or (2026-11-13) `target_page_selector` is set and the page lacks it, whatever template matches | — |
| `fetch_failed` | No usable response after `max_retries` | No (retry, proxy tier) |
| `blocked` | Challenge or block page that no allowed route step passed | No (protection route) |
| `incomplete` | A template matched; a required field is empty — or (added 2026-11-14) the page shows what the mapping does not read: variant data while the mapping declares no `variants`, or a price while the mapping's price is empty (below) | Yes |
| `no_template` | Looks like a target page, no template matches | Yes (new template) |

A page "looks like a target page" when `target_page_selector` is present, or
its JSON-LD contains one of `structured_data_types`, or it came from `urls`
(`url_list`). Required = listed in the job's `required_fields` or marked
`required` in the template's mapping; "filled" = not `null` and, for
`multiple`, not empty.

**Mapping gaps (added 2026-11-14).** A page whose required fields are all
filled is still `incomplete` when the active mapping misses something the page
shows: `variants_not_used` — in-page variant data (a WooCommerce variation form, a
theme's product JSON, JSON-LD/microdata offers or `hasVariant`: two or more
variants) while the mapping declares no `variants`; `price_not_extracted` — the
page shows a price or a range (as `price_on_page`, 6.5) while no record of it
got the mapping's `price` field. A price on request never counts. Such a page
writes no record yet: it is stored like any `incomplete` page, listed in the
unextracted list with `reason: incomplete`, `mapping_gaps` (the codes) and
`last_error` in plain words ("the page carries variant data (two or more
variants) but the mapping declares no variants; kept for a repair of the
mapping"), and re-extracted after the repair. Gaps count only while a repair can
still fix them: once the template's or the job's repair limits are spent, the
template is given up, or the crawl is cut or stopped before a repair, the pages
kept only for gaps are extracted with the mapping as it is (their records carry
`price_status`) and the timeline says `mapping_gaps_accepted`.

**Stored pages.** Every `incomplete` and `no_template` page is stored as
fetched (whether or not its template has an active mapping) until a new
version extracts it, its template is given up, or the job ends. Beyond
`limits.max_stored_pages_per_job` only the URL is kept and the page is
fetched again after the repair (`counters.refetch_after_repair`; a
`problem` `store_limit_reached` is emitted once). After a
version is activated, the stored pages of that template (for a new
template: every stored `no_template` page) are re-extracted before the job
may complete; a page that still fails stays stored for a later version.

**The unextracted list** (`GET /v1/runs/{id}/unextracted`) holds every URL
that ended without a record and is one of: a fetched page of class
`fetch_failed`, `blocked`, `incomplete` or `no_template` at job end; any URL
from `urls`; any URL from a sitemap. Links found by crawling that were never
fetched, and `not_target` pages, are not listed. `reason`
(`unextracted_reason`): `fetch_failed`, `not_found` (HTTP 404/410),
`blocked`, `incomplete`, `no_template`, `template_failed`, `stopped`,
`robots_disallowed`, `private_address_refused`. A fetched target page
therefore ends either as a record or in this list — except a page whose
record was dropped because the result reached `max_records` (4.8), which is
counted in `counters.records_dropped_over_limit` instead.

URLs from `urls` or a sitemap that were never fetched are listed `stopped`
only after `stopped`, `max_duration`, `max_result_size` or `blocked`; after
`max_records` or `max_pages` they are not listed. A queued `url_list` job
that is stopped lists every URL of its `urls` as `stopped`.

A page counts as a target page by the matching template's own rules
(`match.url_patterns`, `match.selector`; no structured data needed); a page
that matches no template is a target candidate (`no_template`) when
`target_page_selector` is present on it, its JSON-LD contains one of
`structured_data_types`, it came from `urls`, or it matches a non-empty
`url_include`.

**`target_page_selector` gates templates (changed 2026-11-13).** When the job sets
`target_page_selector` (and it parses as CSS), a crawled or sitemap page **without**
it is `not_target` even when a template matches it by `match.url_patterns`: its
links are still followed, nothing is extracted or stored. Pages listed in `urls`
are exempt (the operator named them). `POST /v1/samples` applies the same gate to
the pages it discovers (not to `urls` given in the request or `url_list` URLs).

### 4.6 Repair trigger, problems and the block rule

Numbers come from `GET /health` → `repair`.

- **Incomplete:** for a template with status `ok` or `repaired`, over its
  last `window_pages` matched pages (window cleared after each activation),
  once at least `min_pages` are in the window and the share of `incomplete`
  pages is above `1 − required_fill_threshold`, the service opens a mapping
  request (`reason: incomplete`), sets the template to `repairing` and emits
  `mapping_required`. Other templates keep working. Pages that are
  `incomplete` only for mapping gaps (4.5) do not count in that share;
  instead 3 stored gap pages of a template open the request — and when the
  crawl has finished, one is enough. The request's `failures.gaps` counts
  them by code (`variants_not_used`, `price_not_extracted`), its
  `example_urls` and `samples` list them first (added 2026-11-14).
- **No template:** when `no_template_pages` stored `no_template` pages exist
  and no `no_template` request is open, it opens one
  (`reason: no_template`, `template_id: null`).
- One open request per template, one open `no_template` request per job.
  Every request counts against `max_repairs_per_template` (for an existing
  template) and `max_repairs_per_job` (all). When a limit is spent the
  trigger does not open a request: the template is marked `failed` (a
  trigger by mapping gaps alone does not fail it: its pages are extracted as
  they are, 4.5).
- A request that is `failed` (`POST …/fail`) or `expired`
  (`timeouts.mapping_request_timeout_seconds` passed) marks its template
  `failed` for the rest of the job; for a `no_template` request, no further
  `no_template` request is opened in that job. A `problem` event
  `template_failed` is emitted and the job goes on with the rest.
- **Block rule:** over the job's last `block_window_pages` fetched pages,
  when the share of `blocked` pages reaches `block_share`, a `problem`
  `block_rate_high` is emitted. If at that moment the job already uses its
  highest selected proxy tier and neither the click nor the solver can be
  used any more (not requested, not allowed, or its limit spent), the
  service stops fetching with `stop_reason: blocked`. "Highest tier" is
  judged per host: every host among the blocked pages of the window uses
  the highest selected tier (tiers are kept per host, `www.` and port
  included, not per site key).
- When `clicks_used` reaches `max_clicks_per_job` or `solves_used` reaches
  `solver.max_solves_per_job`, a `problem` `challenge_limit_reached` is
  emitted and that step is no longer used.
- At most one `problem` event per (`problem_code`, `template_id`) per job.

### 4.7 Protection counters

`protection` in the run summary (task document 7.2 point 6):
`challenges_met`; `passed_by_step` keyed by route step
(`protection_step`: `http`, `chromium`, `camoufox`, `next_proxy_tier`,
`wait`, `click`, `solver`) = challenged pages that passed at that step;
`frame_not_found` (click attempts where no challenge frame was found);
`failed` (challenged pages no allowed step passed); `hard_blocks`;
`clicks_used`/`clicks_limit`; `solves_used`/`solves_limit`;
`sessions_retired`; `tier_escalations` (added: moves of a host to the next
selected tier). Each challenged page counts once in `challenges_met`
and once in either `passed_by_step` or `failed`. **A hard block is not a
challenge:** it is counted in `hard_blocks` (and `tier_escalations` when it
moves the host on), never in `challenges_met`, `passed_by_step` or
`failed`; a page that stays hard-blocked ends `blocked`. `steps_allowed` in
`GET /health` lists which steps this service may use at all.

Order of the route inside the browser for a challenge: **wait → next proxy
tier → click → solver** (the free wait first; the click and the solver only
on the highest selected tier). The wait lasts until the challenge clears by
itself, at most the service's `WSS_CHALLENGE_WAIT_SECONDS` (30 s by default since
2026-11-13: a managed challenge cleared itself after 29–30 s on a test site).
A hard block moves the host to the next tier at once, without the wait.
Before anything is judged, a page that has not finished loading (about:blank, Firefox's
"Loading <url>" title, a navigation in progress) is waited for, at most 20 s; one that never
loads fails as "did not finish loading" (retried, then `fetch_failed`), never as a
challenge. The click step looks for the widget once more after the page has loaded. Every
page that ends `fetch_failed` gives one `page_fetch_failed` entry (severity `warning`) in the
run's `errors[]` with the URL and the reason (added 2026-11-13). A session (cookies and the proxy exit it earned
them with) that is hard-blocked, challenged again right after clearance, or
moved to another tier is retired and never presented through another exit;
a sticky session lives at most `sticky_minutes` (and at most 30 minutes or
50 pages).

### 4.8 `max_records`

Counts distinct `record_id`s (`counters.records_extracted`). **The result
holds exactly `max_records` records** (fewer only when the site has fewer).
The service does not start a page that may produce a record while the
records written or pending plus the target pages in progress already reach
`max_records` (admission control; target-ness is judged from the URL before
the fetch, as far as it is knowable). Records that still exceed the limit
(pages that were already in progress, stored pages re-extracted later) are
dropped when the result is written: the first `max_records` in the result's
order (`record_id`) are kept, `records_extracted` and the descriptor's
`record_count` equal the kept number, and the dropped ones are counted in
`counters.records_dropped_over_limit` (they are not listed as unextracted).

### 4.9 Stop on trouble, timeline, completeness, comparison (added 2026-11-14)

**Circuit breaker per host.** Every server error (5xx), timeout or network
error of a page counts; any other answer resets the count. After 5 in a row
(`WSS_BREAKER_FAILURES`) the host is paused for 30 s (`WSS_BREAKER_PAUSE_SECONDS`),
doubling with every further pause; after 3 pauses (`WSS_BREAKER_MAX_PAUSES`)
without a success in between the run stops with `stop_reason: site_unavailable`
and a `problem` event `site_unavailable` naming the host and the last error. A
site that is down is never kept loading.

**Outdated sitemap.** When at least 30% (`WSS_SITEMAP_OUTDATED_SHARE`) of at
least 20 (`WSS_SITEMAP_OUTDATED_MIN`) fetched sitemap URLs answer 404/410, a
`problem` event `sitemap_outdated` is sent once; in `auto` discovery that chose
`sitemap` the job adds the link crawl from the start page by itself
(`resolved.discovery_mode` becomes `sitemap_and_crawl`), otherwise the message
advises Discovery = sitemap and crawl.

**`explanation`** — one or two sentences: while running, the progress; at the
end, why the run stopped and what was collected ("Stopped: the site blocked the
scraper; found 120 target pages, collected 80, 40 not collected: 40 blocked."),
the last problem for `blocked`/`site_unavailable`, the comparison's warning, and
`advice` (what to do next).

**`timeline`** — notable moments, at most 50 (the first 10 and the last 40):
`started`, `resumed`, `discovery_decided`, `first_block`, `tier_change`,
`paused`, `problem`, `repair_requested`, `repair_done`, `stop`, `stopped`,
`finished`.

**`completeness`** — `target_pages_found` = pages collected + the unextracted
list; `pages_collected`; `records` (more than pages with variants);
`not_collected` and `not_collected_by_reason`; a `sentence` ("found N target
pages, collected M, K not collected: … by reason"); while running `progress`
`{collected, expected, estimate, text: "M of N"}` — `expected` from the sitemap or
the URL list once discovery is complete, else what has been found so far
(`estimate: true`).

**`comparison`** — the previous completed run of the same site that was not a
`max_records` trial (and none for a trial run): its `target_pages_found`,
`pages_collected`, `records`, `not_collected`, the `change` (this run minus that
one) and a `warning` when records fell by more than 20% (`WSS_COMPARE_DROP_SHARE`),
saying which it is: fewer target pages found ("the site likely has fewer
products") or found but not collected ("the scraper missed them").

### 4.10 Re-collect the missed pages (added 2026-11-14)

`POST /v1/runs/{run_id}/recollect` with `{profile, platform, reasons?}` and an
`Idempotency-Key` starts a **new run** over the parent's unextracted URLs and unfinished sitemap sources:

- the parent must be `completed` or `failed` (else `409 run_not_finished`);
- URLs: the parent's unextracted entries whose `reason` is in `reasons`
  (default `fetch_failed`, `blocked`, `incomplete`, `no_template`,
  `template_failed`, `stopped`; `not_found` and the refusals only when asked),
  each once, as requested (`requested_url` when it differs), with its
  `source_key` kept as the entry's `key`; none and no unfinished sitemap source → `409 nothing_to_recollect`;
- config: the parent's `config` with `discovery_mode: url_list`, those `urls`,
  `rebuild_mapping: false`, `sitemap_url: null`; everything else (limits,
  fetch mode, browser, protection flags) as the parent's. It is validated
  again like `POST /v1/runs` (e.g. more URLs than `max_url_list_entries` →
  `422`);
- unfinished sources: when `sitemap_discovery.complete` is false, the linked
  run retries failed/pending source files with retained per-source page and child
  offsets. It uses sitemap mode, also queues the selected failed document URLs,
  and gets a fresh 100,000-location / 500-source-file budget. Completed source
  entries and completed ancestor documents are skipped; a restart retains the
  same run's spent budget. A source-only retry is valid with `url_count: 0`;
- mappings: the site's active mappings when the new run starts (a repair
  made during the parent counts);
- secrets: the parent's are gone, so `profile` is sent again;
- the new run has its own result file. Its summary carries `recollect_of`
  (`run_id`, `reasons`, `url_count`, `by_reason`, optional `source_count`); the parent's summary lists
  its re-collect runs in `recollected_by` (`run_id`, `state`, `created_at`).
  Its `run_completed` event carries `parent_run_id`;
- a re-collect run has no `comparison` (4.9) and is never the "previous run"
  of a later run's `comparison`.

Sitemap source coverage is exposed as `sitemap_discovery` on the run and its
completeness report. Missing, inaccessible, empty-body and invalid sources yield
`complete: false` and `outcome: partial`, even with zero records. Valid empty XML
sitemaps and completely filtered inventories can be complete. `capped` and
`cap_reason` distinguish `entry_limit` from `source_file_limit`; the entry budget
counts all locations before filtering. Failed and pending source URLs omit user
information, queries and fragments and include fixed failure reasons. Private
address refusals are listed separately and remain outcome-neutral. Incomplete
source cursors retain a private body fingerprint. A changed body, or a legacy
cursor without a fingerprint, replays that source through queue/ancestor dedup;
replay spends the current run's remaining location budget. Completed sources are
not re-polled: start a fresh full run when a new inventory is required. Finished
parent results are never rewritten.

The same key with the same parent and reasons → `200` with the run created
first (section 5).

### 4.11 Links not followed (added 2026-11-14)

A crawled page's links pass these rules before they enter the queue (sitemap
entries and `urls` are never dropped by them). Each skip is counted per rule
in `counters.links_skipped` (per occurrence). `link_rules_off` (a job
setting, so also per site) switches named rules off; `POST /v1/analyze`
answers `link_rules` with every rule, whether it is on, and its lists.

| Rule | Skips |
|---|---|
| `scheme` | `mailto:`, `tel:`, `javascript:`, `data:`, `blob:`, `file:`, `ftp:`, `sms:`, messenger and app links (`whatsapp:`, `skype:`, `viber:`, `tg:`, `callto:`, `facetime:`, `maps:`, `geo:`, `intent:`, `market:`, `itms-apps:`, `fb-messenger:`, `sip:`, `webcal:` …) |
| `messenger_social` | Links to messengers and share buttons on other hosts (`wa.me`, `t.me`, `m.me`, `viber.com`, `facebook.com/sharer`, `twitter.com/intent`, `pinterest.com/pin/create` …). Other hosts are never followed anyway; this only makes them visible |
| `sensitive_path` | A path segment that is an account, login, cart, checkout, wishlist, compare, search, review-form, newsletter, send-to-friend or print page (`login`, `account`, `customer`, `user`, `auth`, `cart`, `checkout`, `wishlist`, `compare`, `product_compare`, `catalogsearch`, `search`, `review`, `newsletter`, `sendfriend`, `print`, `privacy-policy`, `terms` …). Whole segments only, a page suffix (`.html`, `.php`) allowed; for the action words (`login`, `wishlist`, `compare`, `checkout` …) also a segment that starts with the word and `-`, `_` or `.`. `auth` never matches `authentic` or `author` |
| `action_params` | A query parameter that performs an action: `add-to-cart`, `add_to_wishlist`, `add-to-compare`, `remove_item`, `form_key`, `uenc`, `_wpnonce`, `action` … |
| `file_extension` | Documents, archives, media, images, fonts, `css`, `js`, `json`, `xml`, `txt`, feeds |
| `nofollow` | Every anchor to the URL on the page says `rel="nofollow"` |
| `facet_params` | Filter and sort variants of a listing: `color`, `size`, `price`, `brand`, `material`, `manufacturer`, `dir`, `order`, `orderby`, `sort`, `limit`, `mode`, `view`, `product_list_*`, `min_price`, `max_price`, `filter`, `filter_*`, `pa_*` … Pagination (`page`, `p`) is followed. A shop whose products are reachable only through filters needs `link_rules_off: ["facet_params"]` |
| `trap_budget` | Links of a URL pattern (first path segment — with `/*` when deeper —, and the query parameter names; every URL with a filter written in its path — a `color-…`, `size-…`, `brand-…`, `material-…`, `price-…` segment or `f/<ids>` — counts under one site-wide pattern) whose last `trap_pattern_budget` pages (default 100; reached by links) were no target page and led to no new target page: a suspected trap (endless calendars, filter combinations in the path). Applied once target pages can be told by URL and one was found; a warning `trap_suspected` and a timeline entry name the pattern |
| `dynamic_params` | Not a skip: a query parameter that takes a new random-looking value on most links, on at least 10 paths, is left out when telling pages apart (warning `dynamic_parameter_ignored`). Pagination parameters never |
| `canonical` | Duplicates by canonical address (4.12); counts the duplicate pages |

Session and one-time parameters are dropped from the canonical URL itself
(7.3). Canonical paths, including long opaque-looking identifiers, remain part
of page identity. URL-shape heuristics group suspected traps; they never merge
distinct resource paths. Opaque-looking first path segments share a trap-budget
group, and filters written in the path (`/lights/color-red/size-xl/`) are caught
only by the trap budget.

### 4.12 Duplicates by canonical address (added 2026-11-14)

After a page loads, its `<link rel="canonical">` or the HTTP
`Link: <…>; rel="canonical"` header names its real address; only one on the
same site counts. A declared canonical does not replace the loaded address when
it would remove or change its non-pagination query parameters: `/item?id=2`,
`?edition=…` and `?fit=…` can identify distinct resources even if an SEO canonical
names their parent. Tracking/session parameters are normalized first (7.3).
Query-free path aliases still adopt their canonical address.

For pages reached from links, the sitemap or the start page (never `urls` entries):

- the first page of a canonical address is collected; its records get that
  address as `source_url` (and `record_id`), the loaded address as
  `requested_url`; a later link to the canonical address itself is not
  loaded (`urls_skipped.duplicate`);
- a later page with the same canonical is a **duplicate**: page class
  `duplicate`, not extracted, its links not followed, neither collected nor
  missed in `completeness` (the sentence names how many);
- a target page is compared with the first one before it is dropped: a
  different product (SKU, else title), or a product and a listing under one
  canonical, means the canonical is wrong for that page: it is collected
  under its own address;
- a listing's page N that names page 1 as its canonical is not a duplicate;
- the run stops trusting canonicals (warning `canonical_ignored`, timeline)
  after 3 such mismatches, when more than 20 addresses name one canonical, or
  when 3 product pages name the home page; records keyed by a canonical so far
  are keyed by their own address again, and later pages are told apart by
  their own address only.

`link_rules_off: ["canonical"]` turns this off.

### 4.13 One run per site at a time (added 2026-11-14)

**A start while the site is busy (changed 2026-11-14).** With
`when_site_busy: skip` (the default) `POST /v1/runs` for a site that has a run
`queued`, `running`, `stopping` or `waiting_for_credentials` is refused:
`409 site_busy`, `error.details` {`run_id`, `state`, `started_at`, `created_at`,
`site`}, `message` "A run of <site> is already running since <time> (run <id>);
this start was skipped."; nothing is stored (the same `Idempotency-Key` may be
sent again later). A daily schedule then never piles up runs behind a long one.
With `when_site_busy: queue` the run is stored and waits as described next.

A queued run of a site that has a run `running` or `stopping` waits until that
run ends; queued runs of other sites may start before it. While queued, the
summary (also the answer of `POST /v1/runs`) may have `queued_reason`
{`code`: `same_site_running` | `no_free_slot`, `run_id`, `message`}. A run in
`waiting_for_credentials` does not hold its site. A queued run waiting only for
the scheduler with free capacity has no `queued_reason`; `no_free_slot` requires
all concurrent slots to be occupied by running or stopping jobs. Politeness (delays, 429
back-off, crawl-delay) stays per run; with one run per site at a time a
throttle shared across runs is not needed.

### 4.14 Stall watchdog (added 2026-11-14)

While work is queued or in flight and nothing moves — no page finished, no
record written, no sitemap or robots.txt answered — for `stall_seconds`
(`GET /health` `timeouts.stall_seconds`, `WSS_STALL_SECONDS`, default 900,
0 = off): a `problem` event `stalled` and a timeline entry saying what is
stuck (pages in flight and waiting, the oldest in flight, the browser). Still
nothing after a second period: the run stops with `stop_reason: stalled`
(listed URLs not fetched become unextracted `stopped`); a crawler that does
not end is cancelled. A breaker pause or a 429 back-off, an open mapping
request and stored pages waiting for a repair are waiting, not stalling.

### 4.15 Politeness, page timeout and the automatic slow-down (added 2026-11-14)

**Presets.** `politeness` fills the politeness fields that no layer sets:

| `politeness` | Delay | `max_concurrency` | `max_requests_per_minute` | `page_timeout_seconds` |
|---|---|---|---|---|
| `gentle` | 5–10 s | 1 | 10 | 120 |
| `normal` (default) | 2–5 s | 2 | 30 | 60 |
| `fast` | 0.5–1.5 s | 4 | 120 | 30 |

A field set in a layer wins (when only one delay bound is set and the preset's
other bound would cross it, that bound follows it). robots.txt `Crawl-delay` is
always the floor. The run summary states the result in `politeness`
{`preset`, `text`: "normal: 2–5 s, 2 at a time, 30/min, page timeout 60 s"}.

**Page timeout.** `page_timeout_seconds` bounds one page: the HTTP request and the
browser navigation of a run, and every fetch of `POST /v1/analyze` and
`POST /v1/samples`. A page that takes longer fails like a network error (retried
up to `max_retries`, then `fetch_failed`).

Scripted listing pagination uses the selected timeout for its bounded link-observation
window, with no separate 30-second ceiling. Action/page budgets and the run
`max_duration_minutes` limit continue to apply.

**Automatic slow-down.** Per host the service watches its last 20 pages. When at
least 20 % of them were server errors, timeouts, network errors or unusable
answers (4.16) — or the median response time is 3 times the host's first median
and at least 5 s — the host's delay is doubled (up to 8 times the configured
delay, at least 0.5 s per step), and no new page of the host starts before its
usual answer time has passed, which makes it one page at a time. After 10 clean
pages the factor eases by 1.5 until it is back at 1. It never goes faster than
the configured values. Each change is a timeline entry (`slowed_down`:
"slowed down shop.example: 6 errors in the last 20 pages; delay now 4.0–10.0 s
(one page at a time)", `relaxed`), and while a host is slowed the summary lists it
in `politeness.slowed_hosts` {host: {`factor`, `since`, `reason`}}.

### 4.16 Answers with status 200 that are not the page (added 2026-11-14)

Servers under load answer 200 with an unusable page; the right page comes on the
next try. The service judges every 200 answer before extracting:

| Reason | When |
|---|---|
| `empty` | No text at all, or under 20 characters of text without any page structure |
| `truncated` | No `</body>`/`</html>` while the pages of the same URL shape end with them, or the HTML stops in the middle of the text |
| `error_page` | Error or maintenance words in the title or first heading ("service unavailable", "try again later", "maintenance", "database connection", "Wartungsarbeiten", "réessayez plus tard", "techniniai darbai", "технические работы" …) on a page with little text or far smaller than usual |
| `too_small` | Under 10 % of the usual size of its URL shape (5 or more pages known, usually 5 000 characters or more) |
| `lost_template` | A URL shape that was a target page 5 or more times (never anything else) answers without its template's marks |

Such an answer is retried like a server error: the same route, a growing back-off,
at most `max_retries` times; it counts in `counters.soft_errors` and
`soft_errors_by_reason`, in the host's breaker (4.6) and in the automatic
slow-down; the first one is a timeline entry `soft_error`. After the retries the
page is `fetch_failed` with `last_error` "unusable answer: …" — never
`incomplete`, so it does not count towards a mapping repair, and a listing is
never read without its links. In `fetch_mode: auto` a near-empty static answer
first goes to the browser, as before.

**Before a repair.** When the share of incomplete pages opens a repair
(4.6), up to 5 of the pages that triggered it are fetched once more first (a
timeline entry `repair_check`). A page that is fine now writes its record and no
longer counts; the request is opened only if the share is still over the
threshold; otherwise `counters.repairs_avoided` counts it. Repairs opened by
mapping gaps (4.5) and at the end of a cut crawl skip this check.

## 5. Idempotency

**Starting a job.** `POST /v1/runs` requires the header
`Idempotency-Key`, pattern `^[A-Za-z0-9:._-]{1,255}$`. The extension builds
it as

```
fs:<platform job_id>:<step_id>                    # normal step
fs:<platform job_id>:<step_id>:<loop_position>    # inside a loop, e.g. "3" or "2.1"
```

(not the step execution id, which changes on rework and Approval return).
`platform.loop_position` takes only numeric positions
(`^[0-9]+(\.[0-9]+)*$`); when the platform gives no numeric index (a For
each over items without one), send `loop_position: null` and keep the
position only in the `Idempotency-Key` (the key's pattern allows it).
The service stores the key with the run for as long as the run record
exists, together with a fingerprint: SHA-256 of the canonical JSON (sorted
keys, no whitespace, numbers with integral values written as integers) of
`{"config": …, "platform": …}`. `profile` is **not** part of the
fingerprint, so a retry after a credential rotation still matches.

| Request | Answer |
|---|---|
| New key | `201`, a new run in `queued`, `Location: /v1/runs/<run_id>` |
| Same key, same fingerprint | `200`, the existing run summary, whatever its state; nothing changes (the profile of the retry is ignored) |
| Same key, other fingerprint | `409 idempotency_key_reused`, `details.run_id` |
| Missing / malformed key | `400 idempotency_key_required` / `idempotency_key_invalid` |

Two concurrent requests with one key are serialised: one creates, the
other gets the `200` answer.

**Other calls.**

| Call | Safe to repeat? | A repeat returns |
|---|---|---|
| Every `GET` | Yes | Current data |
| `POST /v1/config/validate`, `/v1/analyze`, `/v1/mappings/test`, `/v1/proxies/test`, `/v1/solvers/test` | Yes (no state written) | A fresh answer |
| `POST /v1/samples` | Yes | New samples with new `sample_id`s; older ones stay valid until they expire |
| `PUT /v1/sites/{site}/mappings` | Yes | `200 changed: false` if the content equals the active version (section 6.2); a stale `expected_version` with other content is `409` |
| `POST /v1/runs/{id}/stop` | Yes | `200`, current summary |
| `POST /v1/runs/{id}/resume` | Yes | `200`, current summary; secrets are replaced again with the same values |
| `POST /v1/events/{id}/claim` | Yes, by the same `claimant.job_id` | `200` with the same `claim_id` while that claim is current |
| `POST /v1/events/{id}/stage` | Yes | `200`, unchanged; the first `recorded_at` is kept |
| `POST /v1/events/{id}/complete` | Yes, with the same `claim_id` | `200`, the `handled` event |
| `POST /v1/mapping-requests/{id}/fail` | Yes | `200`, the `failed` request |
| `POST /v1/events/{id}/resend` | **No** — each call is a new delivery generation | Pass `expected_generation` to make a double click harmless (`409 event_generation_conflict` on the second) |

`start_run` is also declared in the extension's `external_effects`, so the
platform's own ledger refuses a duplicate before it reaches the service.

## 6. Mappings

### 6.1 Format

`mapping.schema.json`: one object per template of a site —
`schema_version: 1`, `template_id` (`^[a-z][a-z0-9_]{0,63}$`), `label`,
`match`, `fields[]`.

**`match`.** `url_patterns` (regexes searched in the canonical URL; any
may match) and/or `selector` (CSS selector that must be present); at least
one; every given condition must hold. When several templates of a site
match a page, the first in ascending `template_id` order wins, at run time
and in `POST /v1/mappings/test` alike.

**`fields[]`.** `name` (unique in the template), `type`, `required`,
`multiple`, `sources[]` (1–5, tried in order; the first that yields a
value — for `multiple`, at least one value — wins).

**Sources** (`kind`):

| `kind` | Needs | Reads |
|---|---|---|
| `jsonld` | `schema_type`, `path` | The first JSON-LD node (document order, nested nodes and `@graph` included) whose `@type` is or contains `schema_type`, then `path`: dot-separated property names, a number selects an array item, `*` all items. An array met without index or `*` yields its first item (all items for `multiple`). Objects with `@value` yield that value; objects with `@id`/`url` but no `@value` yield `url`, then `@id` |
| `css` | `selector`, `extract` | First match (all matches for `multiple`); `extract`: `text` (text content), `html` (inner HTML), `attribute` (needs `attribute`) |
| `meta` | `name` | `content` of the first `<meta>` whose `name`, then `property`, equals `name` |
| `spec_table` (added 2026-11-14) | `row_selector`, `key_selector`, `value_selector` | A specification table as pairs "name → value": one per row matched by `row_selector`, the texts of `key_selector` and `value_selector` inside it (a trailing `:` of the name dropped; the first value of a repeated name wins). For a `spec_table` field only |
| `microdata` (added 2026-11-13) | `schema_type`, `path` | schema.org microdata (`itemscope`/`itemtype`/`itemprop`) read as JSON-LD-like nodes: the same node and path rules as `jsonld` (`offers.price`, `image`) |

`extraction_mode` of the job filters sources: `structured_data` → only
`jsonld` and `microdata`; `selectors` → only `css`, `meta` and `spec_table`;
`auto` → all.
Keep structured data first and HTML as the fallback; give a required field a
second source.

**Variants (added 2026-11-13).** An optional `variants` block makes
one record per variant of a product page (`item_index` = the variant's
position, `record.variant` = `{index, count, source, options, id}`); the page's
fields are repeated on every variant record with the variant's own values over
them. A page whose sources yield no variant stays one record (`item_index` 0,
no `variant`). `variants.sources[]` (1–5) are tried in order; the first that
yields at least one variant wins:

| `kind` | Needs | Reads |
|---|---|---|
| `embedded_json` | `selector`; `attribute` (else the element's text); `path` to the list | JSON inside the page: WooCommerce `form.variations_form[data-product_variations]` (HTML-escaped JSON; option slugs are shown with the words of the form's `<label>` and `<select><option>`), a Shopify theme's `<script type="application/json">` product block (`path: variants`) |
| `shop_json` | `platform`: `shopify` or `woocommerce` | The shop's own product JSON: Shopify `/products/<handle>.js` (the handle from the page URL); WooCommerce Store API `/wp-json/wc/store/v1/products/<id>` (the id from the page: `add-to-cart`, `data-product_id`, `postid-N`, the shortlink) and one more request for its variations (`?type=variation&include=…`). Requests go through the page's own session and proxy tier, after robots.txt and the host's politeness delay; for a host that needed the browser only through the cleared browser context — if that is not possible, the next source (in-page) is used and the job log says so |
| `jsonld`, `microdata` | `schema_type`, `path` | `offers` as a list (two or more; one offer is the product's price, not a variant list), or a `ProductGroup`'s `hasVariant` (options from `variesBy`, else `color`/`size`/`material`/`pattern`); an offer's option is its release format (`musicReleaseFormat`: `CD`, `Vinyl`), else `color`/`size`/…, else its name |

`format` (`embedded_json`: `auto`, `woocommerce`, `shopify`, `generic`) says how
one variant reads. `price_divisor` divides prices given in minor units (Shopify
JSON: 100 by default — `1099` is `10.99`; the Store API uses its own
`currency_minor_unit`); `currency` fixes the currency for data that carries none
(Shopify's product JSON — or let the page's `currency` field stand).

Every variant is normalised to `id`, `title`, `options` (name → value, the
shop's words), `price`, `regular_price`, `currency`, `sku`, `barcode`,
`availability` (`InStock`/`OutOfStock`/…), `in_stock`, `weight` (Shopify: grams,
`"52 g"`), `description` (text), `image`, and `raw` (the source's own object).
`variants.fields[]` say which record field takes what: `{name, path}` (a
normalised key or `raw.<path>`) or `{name, option}` (an option by name,
case-insensitive), optional `type` (default: the mapping field's type, else
`text`) and `transforms`. Without `variants.fields`, the mapping's fields named
`price`, `currency`, `sku`, `barcode`, `gtin`, `availability`, `weight`,
`description`, `image`, `image_url` take the variant's value of that name. A
variant value that is empty keeps the page's value; a name not among
`fields[]` adds a field only variants fill (`null` on pages without variants).
Variant identity is the position (and `variant.id`), never the SKU: shops
often repeat the parent SKU on every variation. The required fields are judged
on the first variant's record. Stored pages re-extracted after a repair use the
in-page sources only (a `shop_json` source needs the live page).

**Transforms** (closed list, applied in order to each extracted string; no
expressions, no code):

| `op` | Parameters | Effect |
|---|---|---|
| `trim` | — | Strip Unicode whitespace at both ends; collapse inner runs to one space |
| `regex_extract` | `pattern`, `group` (default 1; 0 = whole match) | Python `re.search`; no match → no value |
| `number` | `decimal_separator`: `auto` (default), `dot`, `comma` | First number in the string; spaces, NBSP, thin spaces and `'` removed. `auto`: with both `.` and `,` the last one is decimal; with one kind occurring once followed by exactly three digits it is a thousands separator; otherwise decimal |
| `price` | `decimal_separator` | Like `number` after removing currency symbols, codes and words; the first amount only (`24,00 € 35,00 €` → 24). Since 2026-11-14 a range — two amounts joined by `–`, `—`, ` - `, `through`, `to`, `bis`, `iki`, `до`, `līdz`, the second higher — gives its lowest value, and the record says `price_status: range` with `price_max` (6.5) |
| `currency` | `default_currency` (ISO 4217) | A three-letter ISO code in the text wins; else the service's fixed symbol table (at least `€ £ ¥ ₽ ₴ zł Kč Ft CHF`); `$` and `kr` resolve only through `default_currency`; else `default_currency` — a last resort since 2026-11-14: the page's own currency replaces it when the page names one elsewhere, it is dropped on a record without a price, and a record that keeps it says `currency_from_default: true` (6.5); else no value |
| `absolute_url` | — | Resolve against `<base href>` or the page's final URL; result must be http(s), else no value |
| `date` | `day_first` (default false) | ISO 8601 or numeric `d.m.y` / `m/d/y` / `y-m-d`; output `YYYY-MM-DD` |
| `html_clean` | — | The fixed clean-up of the `html` type (below) |
| `regex_replace` (added 2026-11-14) | `pattern`, `replacement` (default `""`; `\1` back-references), `count` (default 0 = all) | Python `re.sub`, e.g. `-\d+x\d+(?=\.\w+$)` → `""` turns `lamp-300x300.jpg` into `lamp.jpg` |
| `srcset_largest` (added 2026-11-14) | — | The URL of the largest candidate of a `srcset` (`w` widths before `x` densities; no descriptor = `1x`) |
| `join` (added 2026-11-14) | `separator` (default `", "`) | List-level: every match of this source (as with `multiple`), duplicates out, joined into one string; the field holds that string (a one-item list when `multiple`). Use type `text` |

**Images.** All gallery images in one field: `multiple: true` with a
selector that matches every gallery item (duplicates are dropped, order kept), or
`join` for one string. Full size first: read the link or data attribute the zoom
uses (`href` of the gallery link, `data-large_image`, `data-zoom-image`,
`data-src`, `srcset` with `srcset_largest`); rewrite a thumbnail URL with
`regex_replace` only when nothing else exists.

**Types and the final coercion** (applied after the transforms when the
value is still a string; a value that cannot be coerced counts as "no value"
and the next source is tried):

| `type` | JSON value in the record |
|---|---|
| `text` | string, `trim` applied |
| `html` | string of cleaned HTML: structure kept (paragraphs, lists, tables, line breaks, links, images); scripts, styles, event attributes (`on*`), forms, iframes and tracking attributes (`data-gtm*`, `data-ga*`, `data-track*`, `utm_*` query parameters in links) removed; relative `href`/`src` made absolute. Not configurable |
| `number` | number (`number` transform with `auto`) |
| `price` | number in major currency units (`price` transform with `auto`). Since 2026-11-14 a `css` source with `extract: text` reads a price split into tags as one amount: a trailing 1–2 digit part in `sup`/`small` or in an element whose class or id names the minor units (`fraction`, `decimal`, `cents`, `minor`, `kop`, `ct`) is joined with a decimal mark (`24<sup>99</sup>`, `price-whole`/`price-fraction` → 24.99), a part that starts with `,` or `.` is joined as it is (`24<small>,99</small>`, `€<span>1.234</span><span>,56</span>`), other digits in separate tags stay separate amounts. When the block holds a struck-through amount (`del`, `s`, `strike`, `text-decoration: line-through`, a class or id `old`, `was`, `compare`, `strikethrough` — `old-price`, `price-old`, `compare-at`) beside another, the struck-through text and screen-reader copies are left out: the value is the current price (6.5). Other types keep the plain text |
| `currency` | ISO 4217 code, `^[A-Z]{3}$` |
| `url`, `image_url` | absolute http(s) URL |
| `date` | `YYYY-MM-DD` |
| `spec_table` (added 2026-11-14) | object name → value (strings): from a `spec_table` source, or a `jsonld`/`microdata` path to schema.org `PropertyValue`s (`additionalProperty`: `name`/`value`); no transforms. `multiple` does not apply |
| `boolean` | JSON booleans pass; strings `true/yes/y/1/on/ja` → true, `false/no/n/0/off/nein` → false; schema.org `…/InStock`, `…/InStoreOnly`, `…/OnlineOnly`, `…/LimitedAvailability`, `…/PreOrder` → true, `…/OutOfStock`, `…/SoldOut`, `…/Discontinued` → false |

With `multiple: true` the value is an array (possibly empty) of the type's
values; without it, a single value or `null`.

### 6.2 Versions

Mappings belong to a **site and a template**, never to a job. Versions are
integers per (site, `template_id`): the first activation is `1`, each
activation that changes the content adds 1. Numbers are never reused;
superseded versions are kept (no retention). `content_sha256` is the SHA-256
of the canonical JSON of `mapping` (keys sorted, `,` and `:` without
spaces, UTF-8, non-ASCII not escaped).

`PUT /v1/sites/{site}/mappings` with
`{template_id, expected_version, mapping, origin?}`, atomically per
(site, template):

1. Validate (`422`; `template_id` must equal `mapping.template_id`, field
   names unique, at most `limits.max_templates_per_site` templates).
2. If `content_sha256` equals the active version's → `200`,
   `changed: false`, nothing written (whatever `expected_version` says).
   Activating identical content is always a no-op.
3. If the active version (`0` when the template has none) ≠
   `expected_version` → `409 mapping_version_conflict`,
   `details.active_version`; nothing written.
4. Otherwise store version `active + 1` as `active`, mark the previous one
   `superseded`, answer `200`, `changed: true`.

Activating content equal to an older, superseded version creates a new
version number. There are no candidate versions: a mapping that failed its
test is never sent here.

Effect on running jobs of that site: pages extracted after the activation
use the new version; stored pages are re-extracted (4.5); the open mapping
request of that template (or the open `no_template` request, for a new
template) is resolved (`resolved_mapping_request_ids`). On a conflict the
caller drops its candidate; the running job keeps using the version that is
active.

`export_mappings` = `GET /v1/sites` then
`GET /v1/sites/{site}/mappings?versions=active` per site.
`import_mappings` = `PUT` per template with `expected_version` = the
target's current active version (`0` if none).

### 6.3 Mapping test

`POST /v1/mappings/test` applies `mappings[]` to stored samples
(`sample_ids`, from `POST /v1/samples` or a mapping request; an expired or
unknown id → `404 sample_not_found`). Each sample is assigned to the first
matching mapping (ascending `template_id`). Required = mapping fields with
`required: true` plus the request's `required_fields`. Pass rule:

- a field's `fill_rate` = filled samples / matched samples of its template;
- a template `passed` = it matched at least one sample and every required
  field has `fill_rate` ≥ `required_fill_threshold`;
- `passed` (overall) = at least one template matched a sample, every
  template that matched a sample passed, and — when
  `require_all_samples_matched` (default true) — `unmatched_sample_ids` is
  empty.

A template that matched no sample is reported with `passed: false` and does
not affect the overall flag.

**Variants (added 2026-11-13).** For a mapping with `variants`, each sample
result has `variants` (`count`, `source`, `source_index`, up to 20 `items` with
the variant record's `variant` and `data`) and the template result has
`variant_count`, `samples_with_variants`, `variant_sources_used` (samples per
source kind; `none` = no variants) and `variant_fields` (per-variant fill over
all variants of the matched samples). A `shop_json` source uses the shop JSON
fetched with the sample by `POST /v1/samples`; nothing is fetched by the test.
The pass rule is unchanged.

**Empty fields (added 2026-11-13).** For every template that matched at least
one sample, `templates[].empty_fields` lists the mapping's fields that no
matched sample filled (0 of `matched_samples`), and the answer's `warnings[]`
carries one `fields_never_filled` per such template with a plain message
(the fields, the sample count, the required fields the pass rule used). The
pass rule above is unchanged: an empty *optional* field does not fail the
test, but the warning must be shown to the operator — a mapping that fills
only its title "passes" on a run whose required field is just `title`.

**Price and variants (added 2026-11-14).** Each sample result has
`price_on_page` (6.5) and, for a template with a `price` field, the page record's
`price_status` (`price_max`, `currency_from_default` when they apply); variant
items carry their own. A template that matched at least one sample has
`failures[]` (`field_error` objects, also copied to `warnings[]`); any entry fails
the template (`passed: false`) whatever the fill rates, so the mapping is repaired
before it is activated:

- `price_not_extracted` (field `mappings[i].fields[j]`, the price field): the
  mapping has a `price` field, and on at least one matched sample whose page
  shows a price (`price_on_page` `shown` or `range`) no record got one. A page
  whose price is on request, or that shows none, never causes it.
- `variants_not_used` (field `mappings[i].variants`): matched samples carry
  variant data — a variant source with two or more variants in the sample's
  `variant_sources` — and the mapping declares no `variants` block.
- `price_mismatch` (field of the price; added 2026-11-14): the page record's
  price differs from the price the page states for programs (6.5); the message gives
  both values and the source.
- `price_is_old_price` (field of the price; added 2026-11-14): on a sale page
  the mapped price equals the struck-through old price; the message gives the
  current one.

Fields of type `price` and `number` carry `reading_rules` (sample, rule, text) when
a reading was not plain: `minor_units_joined`, or the rule that decided an
ambiguous decimal mark (6.5).

### 6.4 Mapping requests

`GET /v1/mapping-requests/{id}` (`mapping_request.schema.json`) gives
`build_mapping` everything: `reason` (`incomplete` | `no_template`),
`template_id` (`null` for a new template) and `suggested_template_id`,
`previous` (the active version with content, or `null`),
`expected_version` (send it unchanged when activating), `samples` (stored
pages, usable as `sample_ids`), `failures` (fill rates in the window),
`instructions` (the job's `extraction_instructions`, `fields`,
`required_fields`, threshold, `extraction_mode`, `structured_data_types`,
`target_page_selector`). Status: `open` → `resolved` (an activation) |
`failed` (`POST …/fail`) | `expired` (timeout) | `cancelled` (operator
stop). `mapping_required` is the only event a job waits for.

### 6.5 Price status (added 2026-11-14)

A `null` price is never left unexplained. Every record of a template with a
field of type `price` carries `price_status` (record.schema.json); the field it
speaks of is the one named `price`, else the first `price` field.

| `price_status` | Meaning |
|---|---|
| `shown` | The price field has a value |
| `range` | The source read a range: the field holds the lowest value, `price_max` the highest. A variant record that has its own price is `shown` |
| `on_request` | No price, and the product's own content says the price is given on request: an empty price element, or a schema.org offer without a price, together with request wording ("price on request", "contact us for a price", "to find out the price", "Preis auf Anfrage", "prix sur demande", "cena pēc pieprasījuma", …) |
| `missing` | No price and no sign why |

The page's signal is read from the product's own content: the summary block,
else the main region, else the body (a header's mini cart showing `0,00 €` is
not the product's price). Samples give it as `price_on_page`; the mapping test
fails with `price_not_extracted` when a page shows a price that the mapping did
not read (6.3).

**Decimal marks (added 2026-11-14).** `1.234,56` and `1,234.56` are read by
the last mark; `1 299,00` (space, NBSP or `'` between digit groups) is one amount;
only the first amount of a text counts (`24 € 35 €` → 24). A number with one mark
followed by exactly three digits (`1.234`, `1,234`) is ambiguous: the page's
decimal mark decides — `html[lang]` (`de`, `fr`, `lt`, `ru`, … comma; `en`, `ja`,
`zh`, … dot; `-CH` dot), else `og:locale`, else the page's currency (EUR, PLN, RUB …
comma; USD, GBP, CHF … dot); with no hint it is thousands (as before). So
`Price: 1.234` is 1234 on a `lang="de"` page and 1.234 on a `lang="en"` page. The
mapping test names the rule that decided in `fields[].reading_rules`.

**A sale (added 2026-11-14).** The price field holds the current price, never the
struck-through one. When the page or the variant shows a sale, the record also has
`regular_price` (the old price) and `on_sale: true`: a variant's own regular price
(WooCommerce `display_regular_price`, Shopify `compare_at_price`, Store API
`regular_price`) first, else schema.org `offers.priceSpecification` with `priceType`
StrikethroughPrice or ListPrice, else the struck-through amount of the product's price
block — the latter two only when the record's price is the page's current price. A
variable product on sale keeps its lowest current price (and `price_max`) on a page
record. Samples carry `price_details` (`machine_price`, `machine_source`, `current`,
`regular_price`, `on_sale`, `sale_source`).

**Machine-readable prices first (rule for the mapping agent).** A mapping should read
the price the page states for programs first — `[itemprop=price]` `content`, JSON-LD
`offers.price`/`lowPrice`, `meta property=product:price:amount`, `data-price` — and the
visible text only as a fallback. The mapping test cross-checks: `price_mismatch`
when the mapped price differs from the stated one by more than rounding (0.011 or
0.1 %; a `data-*` value in minor units, ×100, agrees), `price_is_old_price` when
on a sale page the mapped price is the struck-through one (6.3).

**Currency.** `default_currency` is a last resort. When a currency field's value
came from it (the text it read named no currency), the service uses the currency
the page names elsewhere — schema.org `priceCurrency`, the
`product:price:currency`/`og:price:currency` meta, a code or an unambiguous symbol
in a price element of the product's own content (as for the signal above). When the
page names none, the default stays and the record says
`currency_from_default: true`. A record without a price gets no default currency
(the field is `null`).

The three keys are also CSV columns (7.5).

## 7. Results

### 7.1 The file

One JSON Lines file per completed job, written once, never changed:

- name `<site>_<run_id>.jsonl` (for example
  `lumen-shop.example_run_01JCXA7Q3M5VZ8K2N4P6R8T0W1.jsonl`); a site key
  with a port writes its `:` as `-` in the file name
  (`shop.test-8601_run_….jsonl`), so the name matches the schema pattern;
  `site` everywhere else keeps the colon;
- UTF-8 without BOM; one record (`record.schema.json`) per line, compact
  JSON, each line ends with `\n` (also the last); an empty result is a file
  of 0 bytes;
- **`record_id` is unique in the file.** Records are written at least once
  during the crawl (Crawlee re-runs pages, the adaptive crawler fetches some
  twice, re-extraction after a repair); when the file is written, one line is
  kept per `record_id`: the one with the highest `mapping_version`, then the
  latest `extracted_at`;
- lines sorted by `record_id` (byte order), so equal content gives an equal
  file and checksum;
- every field of the template's mapping is present in `data`: `null` (or
  `[]` for `multiple`) when not found;
- `source_url` is the canonical URL (7.3); `requested_url` is present only
  when the discovered or listed URL differs from it; `source_key` is present
  only when the job's `urls` entry had a `key`; `item_index` is 0 in version
  1;
- a record of a template with a `price` field has `price_status`, and
  `price_max` / `regular_price` / `on_sale` / `currency_from_default` when they
  apply (6.5, added 2026-11-14).

The size is capped by `limits.max_result_bytes` (default 99 MiB, below the
platform's 100 MiB upload cap on local file storage; see `stop_reason:
max_result_size`), so every result can become a platform artifact and be
read by `tabular_feed` (which reads `.jsonl` as NDJSON).

### 7.2 Descriptor and download

`GET /v1/runs/{id}/result` returns
`result_descriptor.schema.json#/$defs/service_result`: `run_id`, `format`
(`jsonl`), `file_name`, `size_bytes`, `record_count`, `sha256` (lower-case
hex of the whole file), `templates[]` (`template_id`, `record_count`),
`outcome`, `stop_reason`, `created_at`, `expires_at`
(`created_at + retention.result_days`), `download_path`. Before
`completed` → `409 result_not_ready` (`details.state`); for `failed` →
`409 result_not_available`; after `expires_at` → `410 result_expired`.
Added 2026-11-14: `csv` {`file_name`, `size_bytes`, `sha256`,
`download_path`} describes the CSV file (7.5), and `GET …/result` adds
`fetched_at` (the first time the last byte of either file went out; `null`
before).

`get_result` streams `download_path` into a platform artifact (file name =
`file_name`, so `tabular_feed` reads it as NDJSON), checks that the byte
count and SHA-256 equal the descriptor, and returns the root object of
`result_descriptor.schema.json` = the service fields minus `expires_at`
and `download_path`, plus `artifact_handle`.

`GET /v1/runs/{id}/result/download`:

- `200` with the whole file, streamed; headers `Content-Type:
  application/x-ndjson`, `Content-Length`, `Accept-Ranges: bytes`,
  `ETag: "<sha256 hex>"`, `Content-Disposition: attachment;
  filename="<file_name>"`, `Repr-Digest: sha-256=:<base64 of the digest>:`;
- one byte range (`Range: bytes=a-b`, `a-`, `-n`) → `206` with
  `Content-Range`; a range outside the file → `416 range_not_satisfiable`;
  several ranges → `200` with the whole file; `If-Range` with the ETag is
  honoured (mismatch → `200` whole file); `If-None-Match` matching → `304`;
- the file is immutable, so a client may resume an interrupted download
  with `Range: bytes=<received>-` and verify the SHA-256 at the end.
- sending the file's last byte marks the result as fetched (16.3, added
  2026-11-14).

### 7.3 Canonical URL

Both sides and the tests compute it identically:

1. Parse (RFC 3986). Lower-case the scheme (http or https only).
2. Drop user info and fragment.
3. Host: IDNA to ASCII (UTS #46, non-transitional), lower-case, trailing
   dot removed. `www.` is **kept** (unlike the site key).
4. Drop the port if it is the scheme's default (80, 443).
5. Path: empty → `/`. Normalise percent-encoding (decode `%XX` that encodes
   an unreserved character `A–Z a–z 0–9 - . _ ~`; upper-case the hex of all
   other escapes; percent-encode, as UTF-8, any character outside the
   RFC 3986 path set), then remove dot segments (RFC 3986 §5.2.4). Case and a
   trailing slash are kept.
6. Query: split on `&`, drop empty pieces; split each at the first `=` (no
   `=` → empty value, rendered `name=`); normalise percent-encoding of name
   and value as in step 5 (`+` is left as is); drop pairs whose name,
   lower-cased, starts with `utm_` or is one of `gclid dclid fbclid msclkid
   yclid gbraid wbraid _ga _gl mc_cid mc_eid srsltid` or (added 2026-11-14)
   a session or one-time parameter `sid phpsessid jsessionid sessionid
   session_id oscsid zenid cfid cftoken form_key uenc ___store ___from_store
   ___sid`; sort the remaining
   pairs by name, then value (code-point order); join with `&`; no pairs →
   no `?`.
7. The URL used is the final one after redirects.
8. (Added 2026-11-14.) Before step 5, a path parameter
   `;jsessionid=…`, `;phpsessid=…`, `;sid=…` or `;sessionid=…` (any case) is
   removed from the path.

A record's `source_url` is this canonical URL of the page — or, when the run
trusts the page's declared canonical address, that address (4.12).

### 7.4 `record_id`

```
material  = canonical_url + "\x1f" + template_id + "\x1f" + decimal(item_index) + "\x1f" + (source_key or "")
record_id = "rec_" + first 32 hex characters (lower-case) of SHA-256(UTF-8 bytes of material)
```

`\x1f` is the ASCII unit separator. `mapping_version` is **not** part of
it, so a repair never changes a record's id, and two runs over the same
pages produce the same ids (a destination can upsert on it). `source_key` is
part of it because one page may be listed under two keys; then two records
with the same `source_url` and different `source_key` are written. Later
versions append further components **only when they are non-empty** (section
14), so every version 1 id stays valid.

Test vectors (computed by the reference implementation used for the
examples):

| Input URL | `template_id` | `source_key` | Canonical URL | `record_id` |
|---|---|---|---|---|
| `https://WWW.Lumen-Shop.example:443/produkt/pendelleuchte-aurora-60?utm_source=sitemap#reviews` | `product` | — | `https://www.lumen-shop.example/produkt/pendelleuchte-aurora-60` | `rec_13819b01fd3b92df84ab95fcc8715cbf` |
| `https://www.lumen-shop.example/ersatzteile/glasschirm-opal-150` | `spare_part` | `A-1042` | (unchanged) | `rec_30246844f630ff27ce6d51d1e11ab79e` |
| `http://www.lumen-shop.example/ersatzteile/./g9-fassung/%7e%61?b=2&a=&utm_medium=x` | `spare_part` | — | `http://www.lumen-shop.example/ersatzteile/g9-fassung/~a?a=&b=2` | `rec_ddad72307321bcfc3dee3bed43d832f6` |

### 7.5 CSV beside JSON Lines (added 2026-11-14)

Every completed run also writes `<site>_<run_id>.csv`, served by
`GET /v1/runs/{id}/result/download?format=csv` with its own `ETag`,
`Repr-Digest`, size and ranges (same rules as 7.2). One row per record, the
same records in the same order as the JSON Lines file.

- UTF-8 with a byte order mark (Excel then reads UTF-8); separator `;`
  (Excel in most European locales splits on `;`, and a decimal comma never
  collides with it; other tools need the separator named, e.g. pandas
  `sep=";"`); fields quoted only when they hold `;`, `"` or a line break; lines
  end CRLF.
- Columns: `record_id`, `source_url`, `requested_url`, `source_key`, `site`,
  `template_id`, `mapping_version`, `item_index`, `extracted_at`; then
  `variant.index`, `variant.count`, `variant.source`, `variant.id`,
  `variant.options` only when a record of the run has a variant; then
  `price_status`, `price_max`, `regular_price`, `on_sale`,
  `currency_from_default` only when a record of the run has a price status
  (added 2026-11-14, 6.5); then
  `data.<field>` for every data field, in the mappings' field order.
- Values: `null` → empty; booleans `true`/`false`; numbers as in JSON (dot
  decimal); lists joined with ` | `; objects (spec tables, variant options)
  as JSON text.
- A text value starting with `=`, `+`, `-`, `@`, a tab or a carriage return
  gets a leading `'`, so a spreadsheet does not run it as a formula. Numbers
  are never changed. Read the JSON Lines file when the exact text matters.
- The CSV is not counted in `max_result_bytes`. It expires and is removed
  with the JSON Lines file.

An empty result has a CSV with the header row only.

## 8. Events

### 8.1 Types and body

The webhook body (`event.schema.json`) is small: no HTML, no records.

| `event_type` | `resource_id` | Extra fields | Emitted when |
|---|---|---|---|
| `mapping_required` | `mrq_…` | `template_id` (repair only), `message` | A mapping request opens |
| `problem` | `run_…` | `problem_code`, `template_id` (if any), `message` | `template_failed`, `block_rate_high`, `challenge_limit_reached`, `store_limit_reached`, `waiting_for_credentials`, `proxy_auth_failed`. Not terminal |
| `run_completed` | `run_…` | `outcome`, `stop_reason` | The job completed (4.3) |
| `run_failed` | `run_…` | `message` | The job failed |

Always present: `event_id`, `event_type`, `run_id`, `resource_id`,
`occurred_at`, `delivery_generation`. The body bytes of one generation are
fixed when the generation starts and are identical on every attempt. There
is no ordering guarantee between deliveries; handlers read current state
through the API.

A `proxy_auth_failed` problem is emitted once per authentication pause. Its fixed,
secret-free message asks to check credentials, the service IP allow-list, and provider
account balance or traffic limits, then Resume after provider access is approved. A 403, Cloudflare challenge, target downtime, proxy timeout or ordinary
tunnel connection error does not qualify. This pause does not escalate a proxy tier,
try a paid fallback, open the target site's breaker, mark a document failed, or seal
source traversal complete. Completed records, pending requests, source checkpoints,
links and runtime budgets remain. Proxy secrets that still decrypt remain `kept`;
only unavailable encryption secrets are `missing`. Resume waits for the old crawler
to release its queue before starting its replacement. Running time excludes the
pause; page attempts, navigation actions, record limits, clicks and solves retain
their existing budget usage, including across a service restart. A replacement
proxy/solver profile updates both its public summary and whether the next runner
requires decrypted secrets, so approved endpoint and authentication-mode changes
apply on Resume. A webhook-only Resume keeps the current proxy/solver profile. Chromium's native
browser guard answers only browser-reported proxy authentication challenges, with
the current proxy session's already formatted credentials. Origin authentication
never receives those credentials. Proxy rejection uses explicit 407/challenge
evidence; Chromium's generic invalid-credentials or response-failure errors alone
do not identify a proxy failure.

### 8.2 Event states

`event_state`: `pending`, `delivered`, `claimed`, `handled`, `stale`.

| From | To | Trigger |
|---|---|---|
| — | `pending` | Event created (generation 1) |
| `pending` | `delivered` | A delivery attempt got a 2xx |
| `pending`, `delivered` | `claimed` | `claim` (a claim also marks a pending event delivered and stops its retries — the 2xx may have been lost) |
| `claimed` | `handled` | `complete` with the current `claim_id` |
| `claimed` | `stale` | `expires_at` passed without `complete` |
| `stale` | `claimed` | `claim` by the same `claimant.job_id`, or `stage` with the current `claim_id` (the holder was slow, not dead) |
| `stale` | `handled` | `complete` with the current `claim_id` |
| any | `pending` | `resend`: the current claim is revoked, `delivery_generation` + 1 |

Nothing re-runs automatically: a `stale` event waits for its holder or for
an operator's resend, because processing a whole result may have external
effects.

### 8.3 Claim, stage, complete

`POST /v1/events/{id}/claim` with `{"claimant": {"job_id", "workflow_id",
"step_id"}}` (the platform job of the handler run):

| Event state | Answer |
|---|---|
| `pending` / `delivered` | `200`: new `claim_id`, `expires_at = now + timeouts.claim_timeout_seconds`, state `claimed` |
| `claimed` or `stale`, same `claimant.job_id` | `200`: the same `claim_id`; `expires_at` refreshed |
| `claimed`, other job | `409 event_already_claimed` (`details.claimant`, `details.expires_at`); the handler run stops |
| `stale`, other job | `409 event_stale`; only a resend lets another run take it |
| `handled` | `409 event_already_handled`; the handler run stops |

The `200` body (`event.schema.json#/$defs/claim_response`) carries the event
body, `claim_id`, `expires_at`, `delivery_generation`, `resend_mode`
(`null` for generation 1) and the **recorded progress**:
`progress.stages[]` (`stage`, `recorded_at`, `claimant_job_id`) and
`progress.last_stage` (`processed`, `completed` or `null`). For
`run_completed`, the workflow skips its processing steps when `last_stage`
is `processed` or `completed`.

`POST …/stage` `{claim_id, stage}` and `POST …/complete` `{claim_id}` need
the event's **current** claim; any other `claim_id` (revoked by a resend,
from another event, or never issued) → `409 claim_superseded`. `stage`
refreshes `expires_at`; `completed` before `processed` →
`409 stage_out_of_order`; a stage already recorded → `200`, unchanged.
`complete` on a `handled` event with the same `claim_id` → `200`. Stages may
be recorded for any event type; the templates use them for `run_completed`.

Claim timeout: `timeouts.claim_timeout_seconds` (default 6 hours), counted
from the claim or the last stage.

### 8.4 Resend

`POST /v1/events/{id}/resend` with `{mode, webhook, revoke_live_claim?,
expected_generation?}`, an operator action on the run page:

- `webhook` carries the connection's **current** URL and signing secret;
  they replace the run's stored ones (so a resend works after the
  job-secret key was lost or the secret was rotated);
- a `claimed` event whose claim has not expired needs
  `revoke_live_claim: true` (the page shows the claiming job and asks), else
  `409 event_claim_live`;
- the current claim is revoked (its `claim_id` now gets `claim_superseded`),
  `delivery_generation` + 1, state `pending`, delivery starts at once;
- `mode: resume` keeps the recorded stages; `mode: from_start` clears them,
  so the next handler runs every step again;
- allowed in every state, `handled` included.

### 8.5 Delivery

`POST <webhook.url>` with headers `Content-Type: application/json`,
`X-Scraper-Signature`, `X-Scraper-Body-Signature` (9), `X-Scraper-Timestamp`,
`Idempotency-Key: <event_id>.<delivery_generation>` and
`User-Agent: web-scraper-service/<version>`. Redirects are not followed.

- **Accepted** = any `2xx` within `webhook_delivery.timeout_seconds`
  (10 s). Everything else (other status, timeout, connection error) is a
  failed attempt.
- **Schedule** (`webhook_delivery.schedule_seconds`, ±10 % jitter): attempts
  at 0, 10 s, 30 s, 1 min, 2 min, 5 min, 10 min, 20 min, 30 min, 60 min after
  the generation started, then every 60 minutes until accepted or until the
  job record's retention ends. Each next attempt is planned from the
  previous attempt by the gap between two offsets, so after an outage the
  remaining attempts keep their spacing (no burst). Each attempt is signed
  again with the time of that attempt.
- After a service restart, pending deliveries continue at once, those of
  finished jobs included. Without a usable signing secret (key lost) an
  event stays `pending` with `delivery.last_error:
  signing_secret_unavailable` until a resume or resend brings the secret,
  or the service starts again with the key that decrypts it.
- `delivery` in the event record shows `generation`, `attempts`,
  `last_attempt_at`, `last_status_code`, `last_error`, `delivered_at`,
  `next_attempt_at`.

## 9. Webhook signing

```
timestamp = decimal Unix time in seconds at this attempt, e.g. "1794915070"
signed    = ASCII(timestamp) + "." + raw body bytes
signature = lower-case hex( HMAC-SHA256( key = UTF-8 bytes of webhook.signing_secret, message = signed ) )

X-Scraper-Signature: <signature>          (64 hex characters, no prefix)
X-Scraper-Timestamp: <timestamp>
```

Every attempt and every resend gets a fresh timestamp and signature; the
platform accepts a timestamp only within its tolerance (300 s by default),
so the service host must keep its clock NTP-synchronised.

**Platform trigger configuration** (`Scraper events` → Workflow settings →
Triggers → incoming webhook):

| Setting | Value |
|---|---|
| Auth mode | **Signed webhook (HMAC)** (`webhook_signature`) |
| Signing secret | **Generate a new signing secret**; copy it into the connection's webhook signing secret, and the webhook URL into the connection's webhook URL |
| Signature source / header | `header` / `X-Scraper-Signature` |
| Signature parser | `raw` |
| Digest encoding | `hex` |
| Timestamp source / header | `header` / `X-Scraper-Timestamp` |
| Timestamp unit | `seconds` |
| Tolerance | 300 (default) |
| Signed payload | timestamp, literal `.`, raw body |
| Idempotency mode | `header` (the platform de-duplicates on `Idempotency-Key`, i.e. per event **and generation**, so a resend starts a new run and a repeated attempt does not) |
| Input mapping | `body.event_id` → `event_id`, `body.event_type` → `event_type`, `body.run_id` → `run_id`, `body.resource_id` → `resource_id` |

The same as stored configuration:

```json
{
  "auth_mode": "webhook_signature",
  "auth_config": {
    "signature": {"source": "header", "header": "X-Scraper-Signature", "parser": "raw", "encoding": "hex"},
    "timestamp": {"source": "header", "header": "X-Scraper-Timestamp", "unit": "seconds", "tolerance_seconds": 300},
    "signed_payload": {"parts": [{"source": "timestamp"}, {"literal": "."}, {"source": "raw_body"}]}
  }
}
```

Test vector: secret `fs_whsec_3b1f0e6c9a2d47f8b5c1d0e9`, timestamp
`1794915070`, raw body (one line, no trailing newline)


## 10. Secrets

Secret fields (`writeOnly` and `x-secret: true` in
`connection_profile.schema.json`): `proxy_tiers[].username`,
`proxy_tiers[].password`, `proxy_tiers[].proxy_urls`, `solver.api_key`,
`webhook.signing_secret`.

They reach the service only inside a `profile` (or, for resend, `webhook`)
of these requests:

| Request | Use of the secrets |
|---|---|
| `POST /v1/runs` | Stored encrypted with the job (lifetimes below) |
| `POST /v1/runs/{id}/resume` | Replace the stored ones |
| `POST /v1/events/{id}/resend` | Replaces the run's stored webhook URL and signing secret |
| `POST /v1/proxies/test`, `/v1/solvers/test`, `/v1/analyze`, `/v1/samples` (tests) | Used for that request only, held in memory, discarded when it ends |
| `POST /v1/config/validate` | Presence checked only |

They are never returned by any endpoint (the run shows
`profile_summary`: tiers, providers, geo, counts — no credentials), never
written to a log, an error message, an event or a run summary.

Stored secrets are encrypted on the volume with a key supplied to the
container from outside the volume (the service README names the variable).
Without a configured key the service refuses `POST /v1/runs` and `resume`
with `503 secrets_key_unavailable`.

| Secret | Kept until | `secrets.*` in the run summary |
|---|---|---|
| Proxy credentials, solver key | The job reaches `completed` or `failed`; then deleted from the volume | `proxy_and_solver`: `kept` → `discarded` (`not_configured` when the profile had none) |
| Webhook signing secret (and URL) | The job record's retention ends (`retention.job_record_days` after `finished_at`), because pending deliveries and every resend must still be signed | `signing_secret`: `kept` |

After a restart with the same key everything continues by itself. With a
missing or changed key, `secrets.*` show `missing`; a job that needs proxy
or solver secrets becomes `waiting_for_credentials`; undelivered events stay
`pending`. `resume` (from the connection) restores both; `resend` restores
the signing secret for that event's run.

## 14. Room for later versions

Each of these is additive and needs no change to version 1 shapes:

- **Several products per page.** A template gains an optional
  `items: {"selector": …}` (scope for the fields); records get
  `item_index` > 0, already part of `record_id`. Absent `items` = one item,
  exactly version 1.
- **Variants.** A new field type `group` with nested `fields` (and
  `multiple`) inside a mapping, or one record per variant with an optional
  `variant_key` appended to the `record_id` material only when present.
  Readers already ignore unknown record fields.
- **Login before scraping.** A `site_credentials` secret block in the
  connection profile and a `login` object in `job_config` (new optional
  fields; the session store already keeps cookies per session).
- **More challenge types.** New values of `solver_challenge_type` and
  `challenge_kind`.
- **Named proxy profiles** (task document 5.2): `proxy_tiers[]` entries gain
  an optional `name`, and `job_config` an optional selector by name.
- **A review step on repairs:** nothing in the service; the `Scraper events`
  workflow inserts it before `activate_mapping`.

## 15. Decisions taken while writing the contract

Numbers and choices the task document left open, and the places where it
had to be interpreted:

1. **Webhook headers** `X-Scraper-Signature` (raw lower-case hex, no prefix)
   and `X-Scraper-Timestamp` (seconds); platform parser `raw`, encoding
   `hex`, timestamp from header.
2. **De-duplication per generation.** The task asks for the webhook's
   de-duplication by event id *and* for resends; de-duplicating on the bare
   event id would swallow every resend. Deliveries therefore carry
   `Idempotency-Key: <event_id>.<generation>`, the platform trigger uses
   idempotency mode `header`, and the body carries `delivery_generation`.
3. **Retry schedule** 0, 10 s, 30 s, 1, 2, 5, 10, 20, 30, 60 min, then hourly
   until the job record's retention ends; 10 s timeout; ±10 % jitter; any
   2xx accepted.
4. **Timeouts:** claim 6 h (refreshed by `claim` of the same job and by
   `stage`); mapping request 1 h.
5. **Retention:** result 14 days (default), job record and
   event journal 30 days, stored pages 7 days after the job ends, samples
   24 h. Mappings: no retention.
6. **Result limit** 99 MiB (103,809,024 bytes), just under the 100 MiB
   upload cap.
7. **Service limit defaults** as in section 12 (100,000 pages, 24 h, 16
   concurrency, 2 concurrent jobs, 50 queued, 600 requests/min, 50,000
   listed URLs, 20 samples, 100 clicks, 100 solves, 5/20 repairs, 2,000
   stored pages, 16 MiB request body, 20 templates per site, 64 KiB
   distilled HTML).
8. **Job defaults** not given by the task: `max_pages` 10,000,
   `max_concurrency` 4, `max_requests_per_minute` 60, `sample_count` 5,
   `required_fill_threshold` 0.9, `max_clicks_per_job` 20,
   `solver.max_solves_per_job` 20, `max_repairs_per_template` 2,
   `max_repairs_per_job` 5, `max_duration_minutes` 720,
   `wait_for_selector_ms` 10,000, `wait_after_load_ms` 0;
   `required_fields` default `["title"]`. Task defaults kept: discovery and
   fetch `auto`, browser `camoufox`, delay 1–3 s, retries 3, block heavy
   resources on, refinements 2.
9. **`use_proxy_tiers`.** The `Site settings` entry the task calls
   `proxy_tiers` (which tiers to use) is renamed, so that `proxy_tiers`
   means only the profile's tier list.
10. **Max solves** live only in `solver.max_solves_per_job`, max
    clicks only in `job_config.max_clicks_per_job`, so no field exists twice.
11. **Added endpoints.** `POST /v1/mapping-requests/{id}/fail`: the task's
    `Scraper events` branch 3b says "not passed: report to the service" but
    6.8 has no call for it. `GET /v1/sites`: `export_mappings` (10.1) needs
    the list of sites; import is `PUT` per template.
12. **Added `stop_reason: blocked`.** Task 7.2 point 6 says a site that
    challenges every page "ends the job", but section 9's list has no value
    for it. Rule in 4.6.
13. **"Ignored unless allowed"** (`challenge_click`, `use_solver`,
    `respect_robots: false`) is implemented as a warning plus the corrected
    merged value, so the user sees it. The rotating-proxy refusal (task
    7.2 point 4) applies only when the click or solver is requested and
    allowed.
14. **`validate` answers 200** with `valid`, `errors`, `warnings`; field
    errors become `422` only on `POST /v1/runs`. Test endpoints answer
    `ok: false`, not an HTTP error.
15. **`/health` requires the token** (a Bearer token on every API
    call).
16. **Runs take the merged config.** `POST /v1/runs` receives the output
    of `validate` and validates it again; `profile.defaults` is ignored
    there. The idempotency fingerprint covers `config` + `platform`, not
    the profile, so a retry after a secret rotation is not a conflict.
17. **`record_id`** includes `source_key` (a page listed under two keys
    gives two records), is 128 bits, and is derived from the canonical URL
    of section 7.3 with the tracking-parameter list given there. The site
    key drops `www.`; the canonical URL keeps it.
18. **File layout:** sorted by `record_id`; on duplicates the highest
    `mapping_version`, then the latest `extracted_at`, wins; every mapped
    field present (`null` / `[]`).
19. **Outcome:** `not_found` (404/410) entries alone do not make a job
    `partial`; every other unextracted reason, a failed template, or a
    `max_duration` / `max_result_size` / `stopped` / `blocked` stop does.
20. **`max_records`:** exact (amended 2026-11-13, see 4.8): admission
    control before the fetch, surplus records dropped deterministically when
    the result is written and counted in `records_dropped_over_limit`.
21. **Repair trigger:** fires when the incomplete share of a template's
    last 50 pages (at least 10) exceeds `1 − required_fill_threshold`;
    `no_template` after 5 stored pages; block rule 80 % of the last 50
    pages. A failed or expired mapping request gives the template up for
    the rest of the job.
22. **Required fields at run time** = `required_fields` ∪ mapping fields
    with `required: true`; a required name missing from the mapping makes
    every page `incomplete`, which triggers a repair.
23. **Template precedence:** ascending `template_id`, at run time and in
    tests.
24. **Mapping versions:** integers from 1 per site and template; equal
    content to the active version is a no-op even with a stale
    `expected_version`; re-activating an old content gets a new number.
25. **Stale claims** can still be continued and completed by their holder;
    another run needs a resend. A resend over a live claim needs
    `revoke_live_claim: true`; `expected_generation` makes it safe to
    repeat.
26. **Resume** is accepted in every state (it also rotates a running job's
    secrets).
27. **`max_duration_minutes`** counts only time in `running` / `stopping`.
28. **`auto` discovery:** sitemap when it holds ≥ 80 % of the start page's
    target links, both below that, crawl without a usable sitemap.
29. **Download:** single byte ranges, `ETag` = SHA-256, `Repr-Digest`
    header; the unextracted list is also streamable as NDJSON.
30. **Pagination:** cursor, `limit` 50 (max 200), cursors valid 24 h.
31. **Forbidden `headers`:** `Authorization`, `Proxy-Authorization`,
    `Cookie`, `Host`, `Content-Length`, `Transfer-Encoding`.
32. **Private-address refusal** covers every scrape target and redirect
    hop (see 1 for the ranges and the limits inside a job); the webhook URL
    and proxy endpoints are exempt.
33. **Transforms** keep the task's closed list of eight; their parameters
    (`decimal_separator`, `group`, `default_currency`, `day_first`) are
    fixed options, not expressions.
34. **Events:** at most one `problem` per (`problem_code`, `template_id`)
    per job; a `waiting_for_credentials` problem is created (and delivered
    once a secret is back).

## 16. Storage and clean-up (added 2026-11-14)

The service keeps files and rows on its one volume (`WSS_DATA_DIR`, `/data`).
The automatic sweeper removes them by age (`GET /health` `retention`). These
two routes let the extension show what is kept and clean up on demand. Same
bearer token as every other route.

### 16.1 `GET /v1/admin/storage`

`storage.schema.json`. Read-only. No per-file lists.

| Part | Content |
|---|---|
| `volume` | `total_bytes`, `free_bytes`, `used_bytes` of the file system that holds the data directory |
| `total_bytes` | Sum of every kind's `bytes` |
| `kinds.run_working_files` | `jobs/<run_id>`: Crawlee storage and stored pages. One item per run. `active_items` = runs not finished; `orphan_items` = directories without a run record |
| `kinds.result_files` | `results/*` (JSON Lines and CSV). `unfetched_items` / `unfetched_bytes` = files of completed runs the platform has not fetched yet (16.3); `active_items` = files being written; `orphan_items` = files without a run record |
| `kinds.samples` | `samples/*.html` and `*.extra.json`. One item per sample |
| `kinds.protection_screenshots` | `samples/shots/*.png` |
| `kinds.database` | `service.sqlite3` (`main_bytes`), `-wal` (`wal_bytes`), `-shm` (`shm_bytes`); `reclaimable_bytes` = free pages inside the main file, which only VACUUM gives back |
| `kinds.identities` | `identities.json`. Never removed |
| `kinds.other` | Anything else at the top of the data directory. Never removed |
| `runs` | `by_state` (all six states), `total`, `active`, `oldest_finished_at` |
| `retention` | `result_days`, `job_record_days`, `stored_pages_days`, `samples_hours`, `interval_seconds` |
| `last_cleanup` | `automatic` (the sweeper's last pass), `automatic_with_removals` (its last pass that removed something), `manual` (the last applied clean-up); each `null` or `{at, trigger, removed, bytes_freed}`. Kept in the database |

`oldest_at` of a kind is the oldest modification time among its items (a
directory counts with the newest change inside it). Sizes are apparent file
sizes.

### 16.2 `POST /v1/admin/cleanup`

Request `cleanup.schema.json#/$defs/cleanup_request`; answer
`cleanup.schema.json`. A part left out of the request is not touched. An
empty body is a dry run that removes nothing.

| Request part | Removes |
|---|---|
| `run_working_files: {older_than_days}` | Finished runs' `jobs/<run_id>` and their working rows (stored pages, URL list, link backlog). The run, its records and its result stay. Orphan directories by modification time |
| `result_files: {older_than_days, include_unfetched}` | Finished runs' result files (JSON Lines and CSV together). The run stays; its descriptor's `expires_at` becomes the removal time, so `GET …/result` answers `410 result_expired`. Orphan files by modification time |
| `run_records: {older_than_days, include_unfetched}` | Whole finished runs: every row (records, unextracted, events, mapping requests, secrets …), the run directory and the result file. `GET /v1/runs/{id}` then answers `404 run_not_found` |
| `samples: {older_than_hours}` | Samples (files and rows) last written at least that long ago |
| `protection_screenshots: {older_than_hours}` | Screenshots last written at least that long ago |
| `compact_database: true` | See 16.4 |

`older_than_days` counts from the run's `finished_at` (0 = every finished
run). `dry_run` defaults to `true`: the answer then says what would be
removed. The answer:

- `removed` — one entry per requested part: `items` (runs, samples or files)
  and `bytes`. A file counted under one part is not counted again under a
  later one (`run_records` counts only files the other parts left).
- `kept.active_runs` — runs not finished; nothing of theirs was touched.
- `kept.unfetched_results` — finished runs kept because their result was
  not fetched (16.3).
- `compaction` — `null`, or 16.4.
- `bytes_freed` — sum of `removed.*.bytes`, plus `compaction.bytes_freed`
  when applied. A dry run cannot know what compaction frees; read
  `wal_bytes_before` and `reclaimable_bytes` instead.

Never touched: a run in `queued`, `running`, `waiting_for_credentials` or
`stopping` (the service has no `paused` state; a breaker pause happens inside
`running`), a finished run whose runner is still closing, `identities.json`,
unknown files, the database file itself (only through 16.4).

The clean-up and the automatic sweeper never run at the same time: the
sweeper skips its pass while a clean-up runs, and a clean-up waits for a
sweeper pass (and for another clean-up) to finish. An applied clean-up is
recorded as `last_cleanup.manual`; a dry run is not.

### 16.3 When a result counts as fetched

The service cannot see the platform's artifact store. A result counts as
fetched when either holds:

- the service sent the file's last byte in a download answer (`200` with the
  whole file, or a `206` whose range ends at the last byte), or answered `304`
  to `If-None-Match` with the file's ETag — in JSON Lines or CSV (7.5);
- the run's `run_completed` event is `handled` (`POST …/complete`).

A completed run that has a result file and neither of these is
"unfetched". Its result file (and its run record) is kept unless the
request says `include_unfetched: true`. A run that failed has no result and
is never "unfetched". The automatic sweeper does not apply this rule: it
removes result files after `retention.result_days` as before.

### 16.4 Compaction

- `PRAGMA wal_checkpoint(TRUNCATE)` always (in a dry run: `would_run`). It
  writes the WAL back into the database file and empties it. `busy` = it
  could not finish now; nothing is lost.
- `VACUUM` only when no run is active (as above) and the volume has at
  least twice the database file free (VACUUM writes a copy); else
  `vacuum: skipped` with `vacuum_skipped_reason`. While VACUUM runs, the
  service answers nothing else.
- `database_bytes_before` / `_after` are main + WAL + SHM; `bytes_freed` is
  their difference (`null` in a dry run).

Auto discovery source provenance: `sitemap_probe` has the same coverage shape as
`sitemap_discovery` and is retained on summaries and completeness reports. Failed
sources and caps in this initial inspection keep the run partial even when auto
chooses a healthy crawl or a later source body changes. The inspection's source
offsets are reset before actual feeding; they never advance queue checkpoints.
Source-only recollection remains available after a crawl fallback. An optional
default `/sitemap.xml` 404/410 means absent; an unavailable or invalid default
means incomplete source coverage.
